# Проверка исполняемых планов Agent Studio

Утверждённые условия и текущие результаты: [план](AgentStudioExecutionPlan.md).
Навыки профиля: [AgentStudioSkills.md](AgentStudioSkills.md).

## Сервер и Studio

Новая очередь работает через серверные квитанции `execute_agent_command` /
`read_agent_command`, а планирование читает новые поля наблюдений и каталоги.
Поэтому одной замены приложения Studio недостаточно для проверки всей функции:
сервер должен быть собран из совместимого исходного состояния. Тесты ниже создают
отдельный WorldHost с настоящей симуляцией и MCP; адрес production не используется.
Прогон тестов и упаковка Studio сами по себе не обновляют production.

Перед любой компиляцией убедиться, что Unity Editor закрыт, как требует CLAUDE.md.
Сначала собрать и проверить код, затем запускать модели с `--no-build`. Нельзя
пересобирать общие DLL, пока их использует модельный тест. Одновременные тестовые
процессы используют разные каталоги отчётов, результатов и отдельные миры.

```sh
dotnet test Tests/HexLive.AgentHost.Tests --configuration Release --nologo
dotnet test Tests/HexLive.Server.Tests --configuration Release --nologo
```

Обычный запуск тестов не вызывает платные модели: модельные сценарии помечены
`Explicit` и запускаются отдельно по фильтру.

## Настоящая модель

Для каждого нового запуска нужен новый каталог: нельзя выбирать лучшие повторы
из нескольких матриц. Один сценарий содержит шесть случаев — три набора условий,
по два повтора. Фильтр ниже запускает все четыре сценария (24 случая).

```sh
export HEXLIVE_GAMEPLAY_PROVIDER=Codex
export HEXLIVE_GAMEPLAY_MODEL=gpt-5.6-terra
export HEXLIVE_CODEX_SMOKE_EXECUTABLE=/Applications/ChatGPT.app/Contents/Resources/codex
export HEXLIVE_GAMEPLAY_OUTPUT=/private/tmp/hexlive-acceptance-new-run

dotnet test Tests/HexLive.AgentHost.Tests --configuration Release --nologo --no-build --no-restore \
  --results-directory "$HEXLIVE_GAMEPLAY_OUTPUT/test-results" \
  --filter 'FullyQualifiedName~RealModelCoconutDelivery|FullyQualifiedName~RealModelGiftDelivery|FullyQualifiedName~RealModelBedConstruction|FullyQualifiedName~RealModelDeliveryWithLostAcknowledgement'
```

Для Grok используются `HEXLIVE_GAMEPLAY_PROVIDER=Grok`, точный ID модели и
`XAI_API_KEY` из приватной среды процесса. Не записывать ключ в командную строку,
отчёт или репозиторий. Результаты разных моделей оцениваются отдельно.
По умолчанию Codex в harness использует reasoning `low`. Для отдельного сравнения
можно задать `HEXLIVE_GAMEPLAY_CODEX_REASONING=medium` (или другой поддерживаемый
выбранной моделью режим). Новые отчёты записывают `reasoningEffort`; сводка не
объединяет разные режимы. Старые отчёты без поля помечаются `unspecified` и не
смешиваются с новым явно указанным режимом. Настройка приложения игрока не меняется.
Предел решений указан в каждом новом отчёте как `decisionTurnLimit`: 64 для
кровати, 8 для остальных сценариев. Ранние диагностические прогоны кровати
имели предел 32; они не становятся успешными после увеличения лимита.
Ограничение трёх игровых дней, фактической постройки и проверки сна сохраняется.
Wall-clock лимит исполнения сегмента — max(90, 30 + 4 × число объявленных отправок)
секунд: штатный опрос сам занимает около двух секунд на незавершённую команду.
Формула записана в отчёт; прежние прогоны использовали фиксированные 90 секунд.
Модельный таймаут не расходуется на уже принятую очередь; игровое ограничение
трёх дней остаётся отдельной проверкой.

```sh
python3 Tools/agent_gameplay_summary.py "$HEXLIVE_GAMEPLAY_OUTPUT" \
  --output "$HEXLIVE_GAMEPLAY_OUTPUT-summary.json"
```

Сводка требует все четыре сценария и минимум 5/6 успешных случаев в каждом.
Ложное завершение запрещено. Код возврата 1 означает, что общая приёмка не пройдена,
в том числе когда проверялась только часть сценариев. Несколько отдельных каталогов
с разными сценариями можно передать вместе; дубли одного случая отвергаются.

`Planning` / `Incomplete` в промежуточном JSON не означает завершённый тест.
Диагностически остановленный прогон не считается успешным. Промежуточные отчёты
сохраняются атомарно и содержат текущую цель, очередь, подтверждённый прогресс,
квитанции команд и прочитанные справки — их можно разобрать и после остановки. `HEXLIVE_GAMEPLAY_REPLAY`
позволяет воспроизвести решения из старого отчёта без модели; Replay исключён из
модельной приёмки. Полные JSON содержат решения, наблюдения и ссылки на справку,
но не скрытые рассуждения модели.

## Что именно доказывают сценарии

- Кокосы: три настоящих предмета подобраны и выгружены в лагере. Варианты рюкзака
  не во всех случаях вынуждают надевание: три кокоса могут поместиться и без него.
  Расчёт слотов и стеков дополнительно проверяют серверные тесты инвентаря.
- Подарок: выбрана девушка с собственной симпатией агента, прочитаны правила,
  предмет получен и реально передан; зафиксировано `GiftGiven`.
- Кровать: пустая площадка в подготовленном доме должна превратиться в новую
  `bed.basic`; материалы самой кровати не выдаются. Остальные NPC не строят за
  агента. Требуются сон и завершение за три игровых дня. Старые кровати не считаются.
- Resilience: потерян ответ после принятия команды; в вариантах дополнительно
  исчезает предмет или перезапускается runtime Studio. Проверяется отсутствие
  дублирования. Угроза, разговор и явная отмена отдельно проверяются тестами
  непрерывного RunLoop; модельная матрица не является сценарием встречи с волком.

В модельных сценариях игровое время остановлено на inference, а выполнение команд
ускорено. Они проверяют планирование и результат мира, но не доказывают качество
реального времени при задержках провайдера. Для этого нужны отдельные RunLoop и
ручные проверки на тестовом сервере.

## Технический журнал

Runtime пишет `<StateDirectory>/diagnostics/events.jsonl`; для CLI каталог состояния
задаёт `HEXLIVE_AGENT_STATE`. Журнал связан с профилем, миром, NPC, сессией,
ходом, планом, шагом и командой. `runtimeBuildId` различает собранные версии.
Для разбора используются готовая сводка и фильтры по ID из события:

```sh
python3 Tools/agent_diagnostics.py /path/to/state/diagnostics
python3 Tools/agent_diagnostics.py /path/to/state/diagnostics --plan HASH_FROM_EVENT
```

Начинайте с `step.before → step.sending → command.receipt → step.after`:
там видны исход команды, причина отказа и изменения нужд/свободных слотов.
`reference.read` показывает прочитанную версию справки, события модели — задержку
и доступный usage. Отсутствующее число токенов остаётся неизвестным, а не нулём.
Подсказки о повторных отказах или многочисленных запросах без отправки команды
служат поводом изучить трассу, но сами по себе не доказывают баг.

Лимиты по умолчанию: 8 файлов по 8 МиБ, срок хранения 30 дней; очистка выполняется
при записи. Секреты и скрытые рассуждения не записываются. Ошибка записи отражается
как `DiagnosticsUnavailable` в статусе, не отменяя уже выполненное действие.
Полные модельные отчёты тестов хранятся отдельно и содержат больше данных, включая
решения и текст полученной справки; их не следует путать с журналом runtime.

## Упаковка

После успешной сборки использовать только штатный подписывающий упаковщик:

```sh
dotnet build Server/HexLive.AgentStudio --configuration Release --nologo
python3 Tools/package_agent_studio.py --binary-dir Build/dotnet/bin/HexLive.AgentStudio/Release/net9.0
```

Он проверяет сертификат, подписывает приложение и публикует новую версию рядом
с игровыми сборками. Это framework-dependent preview с установленным .NET 9;
подпись Apple Development не означает публичную нотарификацию. Не запускать агента
автоматически и не считать упаковку подтверждением всех модельных сценариев.
