# Bug #388 — запрос предметов из личной памяти

Владелец: `/root/bug_389`. В карточке нет captured context. Реализация
интегрирована после коммитов #393 и #387; проверена 2026-09-10.

## Причина и изменение

`memorySummary` выбирает 24 свежие записи, а `perceptionSummary` — 24 типа
и 3 ближайших экземпляра каждого типа. MCP `visibleItems` исключает
`FromMemory`. Поэтому известный кокос может отсутствовать в кратком контексте,
хотя личная память содержит его. Отдельного запроса по этой памяти не было.

`query_known_objects` читает только личные `KnownObjects` доступного NPC и
статический каталог. Фильтры применяются до выбора ближайших записей; лимит
по умолчанию 16, максимум 64. Ответ сохраняет возраст и происхождение знания.
`lastKnownTileCenter` обозначает центр последнего известного тайла;
`lastKnownJunction` отдельно хранит известный узел. Точной или текущей позицией
предмета центр тайла не является. Live-поля скрытого предмета не читаются.

AgentHost выполняет запрос, только когда его выбрала модель: один read и не
более одного дополнительного решения до TTS, записи памяти и commit хода.
Предварительная речь, мысль и memoryUpserts не публикуются. Чтение не получает
control lease, не меняет controlVersion и не заменяет текущую ходьбу.
Обычное действие из финального решения проходит прежний путь исполнения.

Запрос не создаёт постоянного кэша или работы каждый tick. TTL 2400 тиков,
лимит 256 непостоянных записей и очистка по отрицательным наблюдениям остаются
у PerceptionSystem. Начальное постоянное знание дома может быть больше этого
лимита. Временное хранилище запроса ограничено O(limit); время сканирования
растёт с размером собственной памяти.

## Проверки

Всего **68 уникальных проверок PASS**, сборки без ошибок. Повторные прогоны
одного теста не увеличивают это число.

| Набор | PASS |
| --- | ---: |
| Новые Server `McpKnownObjectObservationTests` | 14 |
| Соседние Server contract/scope gates | 10 |
| Новые Host `AgentObjectKnowledgeTests` | 13 |
| Host `AgentActionContractTests` | 16 |
| Host `AgentActionOwnershipTests` | 9 |
| Host `AgentRuntimeReconnectTests` | 6 |

Server проверяет кокос за пределами прежнего summary, неизменность ответа
после скрытого перемещения/изменения/удаления live-предмета, player scope,
отсутствие lease, типы и границы фильтров, TTL, постоянное знание дома,
усечение и стабильный порядок. Контракт центра тайла проверен отдельно.

Host проверяет query → финальное решение без предварительной TTS и памяти,
сохранение ходьбы, максимум одного чтения, ответы 401/403, терминальный 403
без бесконечного retry, отмену, несовпадение мира, смену attachment и
controlVersion во время чтения. Запросы с 65 строками и с более 64 KiB UTF-8
дают безопасную ошибку и ровно одно второе решение. UTF-8 проверяется на
неэкранированном не-ASCII тексте длиной менее 65536 символов.

Таймаут моделируется `TaskCanceledException`: проверены классификация ошибки
и второе решение. Точность реального таймера 8 с не измерялась; production
использует `CancelAfter(8 s)` и linked token, отмена которого покрыта тестом.
Секретный текст HTTP/exception не попадает в дополнительный запрос модели.

Артефакты в `Build/bug388-validation/`: `server-known-objects.trx` (24 PASS),
`host-known-objects.trx` (44 PASS), `server-known-objects-final.trx` (13 PASS
и описанная ниже ошибка слишком строгого условия),
`server-allocation-final.trx` (исправленный критерий, 1 PASS), одноимённые
логи и `query-profile.json`. Первый Server прогон был до переименования поля;
13 финальных функциональных случаев и отдельный allocator проверяют итог.

## Профиль

Windows, .NET runtime 9.0.20 из `Build/bug389-validation/runtime9`, SDK
10.0.302, Release. Перед каждой CLI-сборкой проверено отсутствие Unity.
Seed 388, одинаковые каталог, NPC, выбранные 16 записей и параметры запроса;
100 прогревочных и 100 измеряемых вызовов. Положительная калибровка
`new byte[4096]` дала 4120 B по счётчику текущего потока.

| Исходная память | B/read | median, µs | p95, µs | max, µs | JSON UTF-8, B |
| --- | ---: | ---: | ---: | ---: | ---: |
| 256 записей | 5472 | 26.3 | 47.2 | 60.8 | 4210 |
| 4096 записей | 5472 | 119.1 | 134.8 | 256.7 | 4211 |

Это измерение reader и размера его JSON с `McpJson.Options`, а не полного
HTTP-запроса, сериализации или модельного хода. Выделения JSON не включены
в B/read. Нулевые выделения или ускорение не заявляются.

На первом прогоне оба sample дали 547200 B за 100 чтений. На следующем
первый sample дал 549512 B, второй — 547200 B: дополнительные 2312 B первого
измерения не означали рост с числом записей. Точный источник этого разового
расхода не атрибутирован. Условие абсолютного равенства было заменено на
проверяемый контракт `large <= small`, без допуска. Один целевой повтор
дал приведённые в таблице 547200 B для обоих sample. Исходный failed TRX
сохранён; идеальная идентичность между всеми прогонами не обещается.

## Ограничения и проверка игроком

Нужны обновлённые Server и AgentHost. Сервер не развёртывался, платные
провайдеры и живая игровая сессия не вызывались; Host проверен на локальных
fake HTTP/providers. Unity UI и Simulation-код не менялись.

Модель должна сама выбрать запрос по личной памяти. Ответ может быть устаревшим:
типовые взаимодействия из каталога не гарантируют наличие, запас ресурса
или достижимость. После запроса уместный `move_to`/`interact` использует
существующие игровые проверки, включая отказ при исчезнувшей цели.
