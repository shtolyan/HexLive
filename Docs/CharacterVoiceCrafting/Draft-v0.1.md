# HexLive — серверный персонаж, голосовое управление и крафт одежды

Статус: **черновик ТЗ v0.1 для обсуждения, НЕ передавать в разработку без следующего поручения Толи**.
Источник: диктовка Толи 10 октября 2026 года, около 03:06, Asia/Ho_Chi_Minh.

Сегодня разрешены только фиксация и проработка документа. Не менять текущий Singapore release, миры, ассеты, конфигурации, ключи, работающих агентов и задачи релиза. Это будущий объём, а не новый критерий готовности текущего релиза.

## 1. Цель и границы достоверности

Игрок создаёт персонажа в WebGL, выбирает стартовый лагерь и общается с ним голосом без локальной Agent Studio и без собственных API-ключей. Профиль, агент, отношения, выполнение действий и учёт расходов обслуживаются сервером. На острове игрок начинает с минимальной одеждой, выживает и создаёт предметы из материалов.

Это продуктово-технический проект решения по диктовке, не результат аудита исходников. Текущие API Agent Studio, модельный ID, совместимость ElevenLabs и провайдерские тарифы ещё не проверены. Ни одна заявленная интеграция этим документом не считается реализованной.

Обозначения:

- **Решение Толи** — явно заданное требование.
- **Предложение** — рабочий вариант Светы, требует согласования до реализации.
- **Открыто** — вопрос, который нельзя закрыть без исследования или решения владельца.

## 2. Зафиксированные решения Толи

### Идея 1: персонаж и агент на сервере

1. Для игры не должна требоваться отдельно запущенная Agent Studio на компьютере игрока. Нужные функции перенести/интегрировать на сервер.
2. Сервер автоматически создаёт корректную структуру хранения персонажа — без ручного создания папок.
3. При создании героя: имя, внешность/скин, мужской или женский вариант; выбор характера из существующих шаблонов, настройки промптов, аналогичные Agent Studio. Распределение очков навыков — часть желаемого создания героя; набор навыков и бюджет ещё не определены.
4. Всё сохраняется на сервере и привязывается к конкретному персонажу.
5. Голосовое общение и управление доступны без пользовательских ключей; оплачиваемые провайдеры подключены со стороны проекта.
6. В качестве быстрого LLM-кандидата Толя назвал GPT-Luna. Это кандидат, не подтверждённый API-ID и не окончательный выбор.
7. Не усложнять первую версию MCP: нужен короткий путь «реплика → разговор и/или игровая команда → действие».
8. Для речи выбран ElevenLabs, чтобы сохранить уже связанные с персонажами голоса. Google Gemini упоминался как возможная альтернатива, но итоговое предпочтение диктовки — ElevenLabs.
9. Разговор потоковый и быстрый, по ощущениям как телефонный звонок. Во время общения должны быть возможны игровые действия.
10. Доверие и отношения начинаются с нуля и живут как серверные параметры, а не как вручную записанная в промпте история отношений.
11. Казахстанский iRob — референс по ощущению общения. Точный проект/ссылка и его устройство пока не проверялись.
12. Считать расходы по каждому пользователю: LLM, голосовые услуги, примерная стоимость и эквивалент в игровых кредитах/монетах.

### Идея 1, стартовый мир и UI

13. Стартовый остров с шестью лагерями.
14. По умолчанию остров без автоматически появляющихся персонажей. Удалить из стартового сценария автоспавн раненой девушки и другие подобные правила. Игрок появляется по входу/созданию персонажа.
15. Это не поручение очистить текущий прод сейчас. «Никого нет» относится как минимум к персонажам/NPC; судьбу животных и ресурсов нужно уточнить отдельно.
16. Красивый и понятный UI: создание героя, выбор лагеря появления, предпросмотр внешности.
17. Не показывать, кто уже находится в лагерях. Раннее предложение показывать жителей отменено Толей в той же диктовке.
18. Выбора одежды на старте нет. Итоговый вариант: мужчина в трусах, женщина в трусах и лифчике; не полностью обнажённые модели. Далее одежду получают в игре.

### Идея 2: крафт

19. Новые low-poly предметы одежды и варианты их цветов должны стать доступны через изготовление.
20. Задействовать ткань: для бинтов нужны ткань и листья. Количества и лечебные эффекты не определены.
21. Для различных изделий использовать верёвку и шкуру; примеры — обувь и рюкзак. Это не означает одинаковый рецепт для всех предметов.
22. Первая итерация изготовления — у костра. Вторая — на отдельной примитивной станции для изготовления одежды.

## 3. Предлагаемая архитектура серверного персонажа

### 3.1 Компоненты

- WebGL: редактор персонажа, микрофон, воспроизведение голоса, отображение состояния разговора и действий.
- Character/Profile service: владение, сохранение, версии профиля, шаблоны характера, навыки, выбранный голос.
- Agent runtime: серверная замена необходимых функций Agent Studio; не обязательно перенос всего desktop-приложения.
- Voice gateway: авторизация голосовой сессии, потоковая речь, прерывания, согласованный voiceId.
- Command adapter: преобразование намерений агента в существующие серверные команды игры.
- Game server: единственный источник истины о мире, предметах, навыках, отношениях и результатах действий.
- Usage ledger: журнал потребления и стоимости с привязкой к пользователю, персонажу и сессии.

Провайдерские секреты хранятся только на серверной стороне. Если выбранный протокол требует прямого подключения браузера к голосовому провайдеру, клиент получает только ограниченный краткоживущий доступ, если провайдер это поддерживает. Наличие этой возможности необходимо проверить.

### 3.2 Предлагаемая модель хранения

| Сущность          | Основные данные                                                                                                                  |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| CharacterProfile  | characterId, ownerUserId, имя, appearanceId, стартовый campId, навыки, personalityTemplateId, пользовательские настройки, версия |
| AgentConfig       | characterId, разрешённые действия, версия базового промпта, voiceId, профиль модели                                              |
| RelationshipState | characterId, interlocutorId, численные параметры доверия/отношений, версия, журнал изменений                                     |
| VoiceSession      | sessionId, userId, characterId, состояние, временные метки, причина завершения                                                   |
| ActionRequest     | actionId, sessionId, тип, аргументы, состояние, результат выполнения                                                             |
| UsageEvent        | eventId, sessionId, provider, model/voice, единицы, оценка/факт, цена и версия тарифа                                            |

Предложение: база — основной источник данных, папки — связанное файловое хранилище. Создание персонажа идемпотентное: повтор запроса не создаёт копии. Пути формируются по внутреннему ID, не по введённому имени. Точный формат папок взять из реального контракта Agent Studio после аудита, а не придумать несовместимый.

Настройки промптов не должны позволять игроку менять права агента или обходить правила мира. Отделить редактируемую личность/стиль от неизменяемых серверных правил.

## 4. Голосовой цикл и игровые действия

Предлагаемый поток:

1. Игрок входит в свой аккаунт и выбирает принадлежащего ему персонажа.
2. Сервер проверяет владение, лимиты и доступность голосового режима.
3. После разрешения микрофона запускается голосовая сессия; при отказе остаётся текстовый ввод.
4. Реплика поступает в разговорный контур; он выдаёт речь и, при необходимости, структурированное намерение.
5. Command adapter проверяет разрешённый тип действия, аргументы, состояние персонажа, дистанцию, ресурсы и ограничения доверия.
6. Игровой сервер исполняет действие и возвращает фактический результат.
7. Агент сообщает именно результат, а не обещает успешное действие до исполнения.
8. Использование и стоимость записываются независимо от игрового результата.

Не выполнять произвольные команды ОС или код из реплики/ответа модели. Набор игровых действий явный и ограниченный. Повторная доставка actionId не повторяет расход предметов или другое действие.

Действие может начаться во время разговора, после распознавания намерения; завершение всей беседы ждать не нужно. Прерывание речи останавливает голосовой ответ, но не откатывает уже совершённое действие. Отмена незавершённого действия — отдельная команда, если игра её поддерживает.

### 4.1 ElevenLabs: два варианта для проверки

- **A, предварительно предпочтительный:** ElevenLabs обеспечивает разговорный/голосовой контур и передаёт разрешённые вызовы действий нашему runtime. Проверить поддержку нужной модели, голоса, потока, interruption, авторизации и тарификации.
- **B:** свой разговорный orchestrator и LLM, ElevenLabs используется для потокового озвучивания привязанными голосами; распознавание речи выбирается отдельно. Использовать, если A не позволяет нужное управление/модель/задержку.

Не запускать две LLM-цепочки на одну реплику без необходимости: иначе увеличатся задержки и стоимость. Название «ElevenLabs управляет» означает вызов проверяемого серверного адаптера, не прямое право менять мир.

### 4.2 Отношения

Решение: исходное состояние нейтральное/нулевое, без заранее заданной близости. Значения хранятся и изменяются сервером; редактирование промпта и повторное подключение их не сбрасывают и не накручивают.

Предложение: модель получает краткий актуальный контекст отношений как данные на ход, но не является их источником истины. Это отличается от хранения отношений в ручном промпте. Необходимо согласовать, допускается ли такое представление; без передачи состояния агенту или серверной фильтрации поведения оно не сможет влиять на диалог.

Открыто: отношения между кем именно — игроком и собственным персонажем, с NPC, между персонажами, с распознаваемыми собеседниками? Не идентифицировать человека по голосу автоматически без отдельного требования. По умолчанию идентичность берётся из авторизованной сессии.

### 4.3 Качество разговора

Предложение: измерять конец реплики → первый звук ответа (p50/p95), время распознавания, ответа LLM, синтеза и подтверждения команды. Начальный ориентир для обсуждения — первый звук обычно до 1,5 секунды и p95 до 3 секунд на согласованном соединении; это цель, не обещание возможностей провайдера. Финальные пороги определить прототипом.

Проверить перебивание, эхо от динамиков, тишину, потерю сети, повторное соединение, несколько вкладок, отказ микрофона и смену устройства. Не оставлять оплачиваемую сессию открытой после отключения пользователя.

## 5. Создание героя и заселение острова

Предлагаемый сценарий UI:

1. Вход → «Продолжить» для существующего героя или «Создать персонажа».
2. Внешность: доступные мужские/женские варианты и скины, качественный low-poly предпросмотр. Стартовое бельё фиксировано, селектора одежды нет.
3. Имя и характер из существующих шаблонов; дополнительные настройки промпта в отдельном раскрываемом блоке.
4. Распределение очков навыков в заданном бюджете, с понятными описаниями. Числа ещё не согласованы.
5. Выбор одного из шести лагерей: карта/названия/описания, но без списка жителей и подсказок о занятости.
6. Подтверждение: сервер атомарно сохраняет профиль, файловую структуру, начальные предметы и точку появления.
7. Вход в мир, краткая подсказка по микрофону и выживанию.

Сервер не отправляет редактору скрытые сведения о жителях лагерей, а не просто прячет их в UI. После появления обычная видимость мира работает по правилам игры.

Пустое начало задаётся шаблоном нового мира, не очисткой мира при каждом входе. Отключаются также отложенные/повторяющиеся сценарии автоспавна NPC, иначе «раненая девушка» вернётся после рестарта. Ранее созданные игроками персонажи не удаляются.

Открыто: один герой на аккаунт или несколько; сохранение тела при выходе; смерть и перерождение; повторный выбор лагеря; перенос существующих героев. До ответа не проектировать скрытый сброс прогресса.

## 6. Учёт использования и игровых кредитов

Вести серверный append-only журнал потребления, отдельно от агрегированной таблицы в админке.

Собирать: userId, characterId, sessionId, requestId, провайдер, фактический model/voice ID, время, входные/выходные/кэшированные токены при доступности, длительность аудио или другие тарифицируемые единицы, фактические данные провайдера, статус, повторные запросы, версия тарифа и валюта.

Не считать, что ElevenLabs всегда тарифицирует токенами или одинаково для разговора и TTS. Единицы и состав включённых услуг проверить для выбранного продукта. Если услуга уже включает LLM/STT/TTS, не начислять их второй раз.

Оценочная стоимость = сумма количества тарифицируемых единиц × ставки их версии. Для неполных данных явно показывать «оценка», а не «списано провайдером». Неизвестная стоимость не равна нулю. Сверка с провайдером уточняет запись, не создаёт дубль.

Предлагаемые отчёты: день/месяц, пользователь, персонаж, сессия, модель/голос, токены, голосовое время, расходы LLM/речи отдельно и общий итог. Фильтры и CSV-экспорт. Статистика игрока показывает только его использование.

Монеты/кредиты: отдельное правило конвертации и отдельный ledger. На первом этапе — измерение и примерный эквивалент; автоматическое реальное списание, покупка кредитов и монетизация пока не утверждены. Предложение: лимиты на пользователя/сутки и сессию; при исчерпании голос завершается понятным сообщением, обычная игра не ломается.

Аудиозапись и полный текст разговоров не обязательны для биллинга. Политику хранения и удаления определить отдельно; секреты и полные приватные реплики в технические логи не писать.

## 7. Крафт новых вещей

### 7.1 Каталог и рецепты

Каждому доступному крафту назначить устойчивый recipeId, результат из нового каталога, материалы и количества, время, станцию, необходимые навыки/условия и разрешённые варианты цвета.

| Результат         | Материалы по диктовке / предложению                      | Что ещё определить                            |
| ----------------- | -------------------------------------------------------- | --------------------------------------------- |
| Бинт              | Ткань + листья — решение Толи                            | Количества, длительность, эффект              |
| Примитивная обувь | Шкура + верёвка — предложение конкретного рецепта        | Точный предмет каталога, цена, характеристики |
| Рюкзак            | Шкура + верёвка; ткань при необходимости — предложение   | Вместимость, цена, визуальная совместимость   |
| Тканевая одежда   | Ткань + подходящие крепления — предложение               | Набор вещей, стоимость, навыки                |
| Цветной вариант   | Базовый предмет + пигмент — предложение, не решение Толи | Источники красителей и число вариантов        |

Провести сопоставление всего нового каталога с рецептами. Не создавать недостижимые варианты цвета и не объявлять каждый mesh самостоятельным предметом без проверки текущей модели инвентаря.

Источники ткани, шкур, верёвок и листьев должны быть доступны в стартовом выживании. Крафт рюкзака не должен требовать объёма инвентаря, достижимого только после создания рюкзака. Проверить базовую цепочку без стартовой одежды и без NPC-помощников.

### 7.2 Станции

Итерация 1 — доступ к изготовлению у костра. Это игровой доступ к меню, не утверждение, что одежда физически создаётся огнём. Определить радиус, необходимость горящего костра и доступность общей станции.

Итерация 2 — предложение: **«Швейное место»**, примитивная рама/рабочая поверхность с инструментами для обработки шкуры и сшивания вещей. Подходит по стилю первобытной общины. Возможные материалы станции: ветки/жерди, верёвка, каменный инструмент; костяная игла — вариант. Это художественно-игровое предложение, не историческая реконструкция.

Ткацкий станок оставить отдельной возможной будущей станцией производства ткани из волокон: шитьё одежды и ткачество не смешивать. В первой версии вводить оба необязательно.

При переносе рецептов с костра на станцию предусмотреть доступный рецепт самой станции; не блокировать базовые бинты и раннее выживание без отдельного решения.

### 7.3 Серверные правила

Сервер проверяет материалы, доступ к станции и выбранный рецепт; списание ресурсов и выдача результата атомарны. Повтор запроса не даёт дубликат. Определить поведение при отмене, смерти, выходе и разрушении станции. Клиент не может выбрать недоступный цвет или произвольно изменить цену рецепта.

Проверить посадку вещей на всех разрешённых телах, цвета, слоты экипировки, совместимость рюкзака с одеждой, карты крови/грязи и отсутствие возврата старых ассетов. Цветной предмет и его вариант сохраняются после переподключения.

## 8. Предлагаемые критерии приёмки будущих задач

### Серверный персонаж и голос

- Новый пользователь без Agent Studio и без API-ключей создаёт героя, заходит и общается через микрофон.
- Повтор создания при сетевой ошибке не дублирует профиль/папку/предметы; продолжение с другого устройства восстанавливает героя.
- Пользователь не получает управление чужим персонажем и не меняет доверие редактированием промпта.
- Выбранный голос сохраняется; потоковый ответ, перебивание и действие работают в одной сессии.
- Реплики «подойди/возьми/поговори» проходят через реальные поддерживаемые команды; невозможное действие получает честный отказ без фиктивного успеха.
- Переподключение не повторяет действие и не списывает использование дважды.
- Отношения исходно нулевые, затем сохраняются сервером независимо от подключения и текста промпта.
- Измерены задержки и расходы; выбранная конфигурация не считается подходящей только по названию модели.

### Остров и редактор

- Новый остров содержит шесть лагерей; при старте и после рестарта нет персонажей, созданных отменёнными сценариями.
- Игрок выбирает лагерь без информации о его жителях; появляется только после подтверждения создания.
- Превышение бюджета навыков отклоняется сервером.
- Стартовая одежда фиксирована: трусы / трусы и лифчик. Полностью обнажённого старта и выбора одежды нет.
- Создание нового героя не очищает мир и не удаляет чужих/существующих персонажей.

### Использование и крафт

- По двум тестовым пользователям расходы не смешиваются; стоимость помечена как оценочная или сверенная.
- Повтор webhook/request не удваивает расходы или выдачу предметов; агрегаты воспроизводятся из событий.
- Бинт расходует ткань и листья; подтверждённые обувь/рюкзак изготовляются из согласованных материалов.
- Вещи и цвета соответствуют новому каталогу и сохраняются после рестарта.
- У костра работают рецепты первой итерации; перенос на станцию проверяется отдельно, без скрытого блокирования выживания.
