# Этапы строительства объектов HexLive

## Готовый файл

Открыть `_ArtSource/Construction/hexlive_construction_stages.blend`.
Все 14 моделей уже разложены по стадиям. Файл открывается на гардеробе,
орбита viewport направлена на него. Исходник находится вне Assets: Unity
импортирует только native FBX, а не пытается конвертировать общую Blender-библиотеку.
В верхнем меню Scene выбрать объект:
`01 Стена` … `14 Гардероб`. Сцена `00 Все объекты` показывает общую витрину
через collection instances. Каждая рабочая сцена содержит одну модель в её нуле.

В Outliner раскрыть `definition id → BuildStage_N__material → children`.
Положение и размеры взяты из текущих игровых native FBX и проверены по
координатам вершин. Это однократная миграция утверждённого арта; далее источник
стадий — сохранённый общий `.blend`.

| Объект | Стадии по порядку |
|---|---|
| Стена и окно | 4 палки → 3 доски → 4 верёвки |
| Дверь | 5 палок → 2 доски → 4 верёвки |
| Опора | 2 палки → пустая совместимая стадия → 3 верёвки |
| Сектор пола | 2 палки → 3 доски → 3 верёвки |
| Оба варианта крыши | 3 палки → 27 листьев → 2 верёвки |
| Домашний очаг | 8 палок → 12 камней → 1 верёвка |
| Кровать | 4 бревна → 5 палок → 10 верёвок → 50 листьев |
| Уличный костёр | 9 палок → 2 стойки → 1 перекладина → 2 верёвки → 18 камней |
| Сушилка | 2 стойки → 2 перекладины → 4 верёвки |
| Сборщик воды | 4 палки → 5 камней → 4 палки → 8 верёвок → 11 листьев |
| Верстак | 4 палки → 2 палки → 2 доски → 2 верёвки → 4 доски |
| Гардероб | 4 части каркаса с ножками → 8 досок полки → 1 составная обвязка |

У гардероба две прежние широкие доски разделены на восемь длинных планок:
каждая опирается на обе нижние поперечины, нет висящих стыков посередине.
Полка опущена на 0,055 wu до касания ножек; её поверхность — `ShoeShelfSurface`.
Ножки доходят до пола и входят в units соответствующих
стоек. Все видимые обвязки находятся под одним `rope_unit_00`: они оплачиваются
одной верёвкой. Шаблон вешалки и сокеты одежды/обуви сохранены как helpers.

## Редактирование

Для простого переноса children достаточно Outliner. Для переноса с сохранением
мирового положения и просмотра стадий использовать подготовленную панель:

1. В Text Editor выбрать встроенный текст `ОТКРЫТЬ ПАНЕЛЬ.py` и нажать Run Script.
   Альтернатива — установить `Tools/blender/construction_stage_authoring.py`
   через Preferences → Add-ons.
2. В 3D Viewport открыть `N → HexLive Build`.
3. Выбрать деталь или parent модели. Root и definition id уже заданы.
4. Выделить части и нажать `Назначить` у нужной стадии. Для нескольких meshes
   одной доставки есть `Объединить в один resource unit`.
5. Кнопки `1/2/3…` показывают результат до выбранной стадии, `Все` — готовую модель.
6. Нажать `Проверить стадии` и сохранить файл.

Один прямой non-deco child стадии = одна единица ресурса. Составная деталь
может быть Empty с вложенными meshes. Порядок внутри стадии задаётся именами
units (`…_00`, `…_01` и т. п.). Blender добавляет одинаковым stage names разных
объектов суффиксы `.001`; панель их понимает, экспортёр выдаёт канонические имена.

Root и stage parents имеют нулевую позицию/поворот и единичный масштаб.
Не двигать их ради перестановки стадий. Сохранять шарнир двери, state markers,
`fire_point`, маркер сна, clothing/shoe sockets и `HangerTemplate`.
Дверной pivot — прозрачный контейнер: его доски считаются обычными units стадии.

Изменение количества частей в стадии меняет рецепт. До экспорта нужно
синхронизировать `Tools/construction_stage_manifest.json` и simulation stages/bill
(`BuildSiteMath`, архитектурные bills). Проверка сообщает расхождение, чтобы
объект не завершился с неоплаченными невидимыми деталями.

## Экспорт и проверка

Flow: сохранённый `.blend` → общий exporter → native FBX → Unity import →
atomic object content → runtime включает установленные units после строительных действий.
AssetBundles собираются и публикуются отдельной явно запрошенной операцией.

В панели есть `Экспорт FBX этого объекта`. CLI для проверки источника:

```bash
/Applications/Blender.app/Contents/MacOS/Blender \
  _ArtSource/Construction/hexlive_construction_stages.blend --background --factory-startup \
  --python Tools/blender/export_construction_stage_workspace.py -- --audit-source
```

Для одного объекта заменить `--audit-source` на `--definition bed.basic`,
для всех — `--all`. FBX пишутся по прежним путям в
`Assets/HexLiveContent/RuntimeSource/Objects`.

Чтобы проверить без замены игровых FBX, добавить
`--all --export-dir /tmp/hexlive-construction-stage-exports`.
Затем отдельным запуском указать
`--verify-export-dir /tmp/hexlive-construction-stage-exports`:
повторный импорт проверит units, вершины и матрицы сокетов/двери.

После интеграции FBX визуально проверять `Assets/Scenes/BuildStagesShowcase.unity`,
использующую те же фабрики, что игра. Сцена не является источником арта.

## Сохранность правок

В manifest `source`/`sourceRoot`/`exporter` указывают на готовый stage workspace.
`geometrySource`/`geometrySourceRoot`/`geometryGenerator` сохраняют происхождение
геометрии. Старый генератор не знает ручную иерархию: не экспортировать им
поверх утверждённых стадий. Правки процедурной геометрии по-прежнему вносить
в генератор, затем переносить только изменённую геометрию в авторские units.

`prepare_construction_stage_workspace.py` — однократный migration tool.
Он отказывается перезаписывать существующий файл, чтобы не потерять правки.
Все 14 моделей экспортированы из stage workspace. Сушилка нормализована вдоль
локальной +Y, одежда читает `DryingSlot_00…07` из того же FBX. Старый контент без
сокетов имеет только fallback; его нельзя считать проверенным новым экспортом.

## Аудит и просмотр каждой детали

В панели есть `0 / −1 / +1`: показать пустую площадку, предыдущую или следующую
оплаченную деталь. Приоритет задан `unit_NN_MMM` в пределах стадии. Перенося
unit, переносить его целиком с детьми. Базовые стойки идут раньше верхних частей,
бесплатная оснастка находится под соответствующим ресурсом, а не на пустой стадии.

`audit_construction_review.py` создаёт `Build/ConstructionReview-20261016/index.html`,
PNG после каждой детали и `audit.json` с грубой проверкой контакта. Это снимки
Blender, не утверждение об успешной Unity-интеграции. Крыша имеет внешние опоры;
геометрический тест не заменяет проверку доступности модуля симуляцией.

Рядом с каждым FBX exporter пишет `.construction.json`: последовательность
`index / stage / resource / count=1 / nodePath`. Она позволяет привязать одно
строительное движение к одной детали, не угадывая ресурс по числу renderers.
Запас доставок остаётся в `Contents`, установленный прогресс — в
`InstalledBuildMaterials`. Один завершённый Build-цикл устанавливает один unit;
пачка доставки не включает сразу всю стадию. Прогресс переживает save v85.
У старых поддерживаемых сейвов сохраняется прежний видимый прогресс, затем
последующие действия учитываются поштучно. Snapshot-каналы `Delivered*` передают
видимую установленную геометрию; фактический запас читает `BuildSiteView.Materials`.

Проверка готовности чужого ПК, упаковка и Player: `Docs/ConstructionBuildHandoff.md`.
`python Tools/construction_content.py verify-source` ничего не собирает;
`plan` только печатает команды, `verify-candidates` отвергает старые бандлы.

`HexLive/Content/Validate Construction Units` в Unity проверяет все 14 моделей,
каждую оплаченную деталь, пустую площадку, иерархию, sockets и export receipts.
Этот gate включён в общий `WorldPropBuildGate`; материалы не проверяются
изолированно без предшествующих стадий. Simulation-тесты сравнивают каталог
и сметы архитектурных модулей с manifest.

Для общего дома `dotnet run --project Tools/ConstructionReview` экспортирует
реальные production modules из `BlueprintBuildingPlan.Modules`, а
`render_production_construction_review.py` делает художественные снимки стадий.
Редактор Unity и production loading path всё равно требуют собственного прогона.
