## §149 Персонаж игрока на сервере — постоянное назначение и будущий отряд (iteration 149)

Сетевой токен §145 открывал игроку дверь управления, но не назначал ему
персонажа: любой авторизованный клиент мог взять временный лиз любой девушки
лагеря. Лиз переживал реконнект по `clientId`, однако после таймаута персонаж
снова становился общим. Для многопользовательского сервера это не владение:
два игрока по очереди могли управлять одной колонисткой, а вернувшийся игрок не
получал ту, с которой уже играл.

### §149.1 Постоянное назначение отдельно от активного лиза

У сервера два разных реестра с разным временем жизни:

- `PlayerCharacterAssignments`: постоянный `playerId → [npcId…]`, хранится в
  `hexlive-players.json` рядом с серверным сейвом и переживает разрыв связи,
  перезапуск клиента и перезапуск сервера;
- `ControlLeases` §145.4: короткий лиз активного ручного управления, защищает
  одну NPC от одновременных приказов игрока и MCP. Истечение лиза возвращает
  NPC под ИИ, но НЕ освобождает постоянное назначение.

Стабильный `playerId` — `X-HexLive-Client-Id`, который клиент один раз создаёт
в PlayerPrefs. Сервер принимает для постоянного владения только канонический
GUID `N` (32 hex-символа): отсутствующий/испорченный id оставляет соединение
обычным зрителем даже при верном общем access-token. Так случайный connection id
не засоряет постоянный реестр и не получает персонажа, которого нельзя вернуть
после реконнекта.

### §149.2 Выдача первого свободного

На каждом авторизованном подключении сервер атомарно сверяет назначение с живым
ростером:

1. Сохраняет уже назначенных NPC, которые всё ещё находятся в
   `world.Entities.Npcs` и принадлежат `Faction.Colony`.
2. Удаляет из назначения умерших (перенесённых в `Corpses`) и тех, кто больше
   не относится к лагерю игрока.
3. До текущего лимита добирает первых свободных по возрастанию `npcId`.
   Свободный = живой, не умирающий NPC `Faction.Colony`, которого нет в
   назначении ни одного другого игрока.
4. Пишет изменившийся реестр атомарно. Если свободных нет, список может быть
   пустым: сервер не крадёт старое назначение отсутствующего игрока.

Текущий продуктовый лимит — **один персонаж на игрока**. Сама операция принимает
`characterLimit` и возвращает список: будущий отряд не меняет формат файла,
handshake, клиентский интерфейс или серверную проверку прав. Контракт проверяется
обоими стартовыми ростерами: при лимите 2 игрок получает `[1,2]` в своём лагере
`BigIsland`, при лимите 1 — `[1]` в `HugeIsland`/`Maniac`.

Если назначенный персонаж умер, следующий вход тем же `playerId` сначала
удаляет мёртвый id, затем выдаёт первого свободного по тому же правилу. Умирающий
по §105 ещё жив и назначение не теряет; нового игрока ему не выдают.

### §149.3 Провод и клиентское право

Wire protocol v9 добавил в `Handshake` список `AssignedNpcIds`; текущий v10
сохраняет его и добавляет персональный `CraftingOptions` §138. Это авторитетные
данные именно данного соединения; они не входят в `WorldSnapshot`, потому что у
разных зрителей одного тика назначения и доступный ручной UI различаются.

`ISimulationSource.CanControlNpc(id)` — единый презентационный предикат:

- local/loopback сохраняют прежнее право на любую живую `Faction.Colony`;
- remote возвращает true только для id из собственного handshake;
- аноним и авторизованный игрок без свободного персонажа не могут управлять
  никем.

Через этот предикат интерфейс решает, показывать ли активный тумблер, разрешать
ли инвентарь и включать ли NPC в ручное/групповое выделение. Сервер всё равно
повторно проверяет каждого актора команды против назначения ДО лиза и ДО
`ManualCommandExecutor`; поддельный клиент получает `NotAssigned`, а групповая
команда отклоняется целиком.

Назначение даёт право переключать своего персонажа между ИИ и ручным режимом,
но само по себе не держит его в ручном режиме. Поэтому отключившийся игрок не
замораживает колонистку: лиз истекает по §145.4, ИИ продолжает жить, а при
возвращении игрок снова видит право на того же персонажа.

### §149.4 Мир и файл

`hexlive-players.json` относится к конкретному серверному сейву так же, как
`hexlive-admin.txt` и `hexlive-player.txt`, и обязан переноситься вместе с ними.
Файл содержит версию схемы и упорядоченный список игроков со списками NPC;
дубликат одного `npcId` у двух игроков при чтении нормализуется в пользу первой
записи, чтобы повреждение файла не создало двойное владение.

Если сервер стартует без существующего сейва, старый sidecar очищается. Команда
админки «новый мир» также очищает назначения одновременно с лизами и закрывает
viewer-соединения; на реконнекте новый мир раздаёт персонажей заново. Обычная
загрузка существующего сейва sidecar сохраняет.

Каждый атомарно снятый viewer-session несёт монотонное поколение мира. Реестр
переключается на новое поколение под тем же замком, что и выдача: запоздалая
сессия старого мира не может вернуть его NPC, а позднее уведомление
`WorldSwapped` не стирает назначение, которое viewer нового мира уже успел
получить.
