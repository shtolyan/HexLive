## §152 Атомарный удалённый контент (iteration 152)

Игровой контент должен обновляться по одному логическому объекту: новая версия
юбки не имеет права требовать нового Player, общего каталога, content release или
пересборки соседних предметов. Player содержит код, минимальный bootstrap и
стабильный клиентский UI и обязательные эффекты, а модели, персонажи, одежда,
волосы, протезы, предметы, здания, мобы, audio и конфигурация приходят из
независимо опубликованных объектов.

### §152.1 Идентичность и версия объекта

Единица публикации — `ContentObject`, адресуемый парой `type/id`. Допустимые типы:
`wear`, `actor`, `hair`, `prosthetic`, `object`, `building`, `mob`, `vfx`,
`audio`, `config`. `id` стабилен во времени (`wear/skirt.anarchy`), а
`revision` — положительное монотонное число. Record содержит `state` (`active` или
`retired`), metadata и варианты payload по `platform/runtimeProfile`; каждый
вариант фиксирует SHA-256 фактических байтов, размер, `payloadType` и имя корневого
entry asset.

Новые id используют машинный формат с точками и дефисами. Существующие стабильные
авторские id с внутренними пробелами сохраняются без массового переименования
сейвов и локализации, но никогда не могут содержать `/`, `\\` или быть путём.

`revision` принадлежит объекту, а не платформенному файлу: одна revision может
иметь варианты для `StandaloneOSX` и `StandaloneWindows64`. Обычная правка mesh,
material, texture или icon не связана с версией Player. Физическую совместимость
Unity bundle задаёт стабильный `runtimeProfile` (первый профиль —
`unity6000-content1`); старый Player выбирает последнюю revision, имеющую
совместимый вариант. Смена content API или формата Unity создаёт новый профиль,
но не общий релиз контента.

Rollback не уменьшает revision: возврат содержимого revision 1 после revision 2
публикует revision 3, которая может повторно ссылаться на старый immutable blob.
Повторная публикация полностью тех же вариантов и metadata является no-op.

Первичное заполнение пустого сервера может оркестрироваться командами
`content build-all` и `content publish-all`. Это не создаёт общий content
release: обнаруженный inventory существует только в build output, каждый
bundle собирается отдельным вызовом классического pipeline с нулём внешних
зависимостей, а сервер назначает revision и переключает record отдельно для
каждого `type/id`. Batch upload лишь дедуплицирует транспорт одинаковых blobs и
запускает один административный процесс вместо тысяч SSH-сессий; ошибка одного
candidate не делает остальные объекты частями общей транзакции.
Авторские `GarmentCatalog` и `ActorAppearanceCatalog` не публикуются: bootstrap
обнаруживает активные определения объектов только во время сборки, а runtime
узнаёт одежду и причёски из независимых live records.
Позднее первичное добавление новой платформы может сохранить уже проверенные
варианты текущей записи только при неизменной metadata. Это создаёт следующую
revision объекта, не заставляет старую платформу скачивать новый blob и не
разрешает частичное семантическое обновление: при изменении metadata publisher
требует заново передать все поддерживаемые платформы.

Варианты macOS и Windows одного bootstrap обязаны быть собраны из одного
точного Git commit, а не просто из одноимённой движущейся ветки. Release owner
сначала объявляет immutable SHA, обе машины переходят на него detached checkout
и сверяют полный `git rev-parse HEAD`, и только затем запускают Unity. Кандидаты
со старого HEAD, из незакоммиченного дерева или из ручной частичной очереди не
смешиваются с этой публикацией. Последующие Player/server commits допустимы в
том же `runtimeProfile`, пока не меняют stable content API; сам SHA исходников
двух платформенных payload всё равно остаётся общим.

### §152.2 Самодостаточный payload и иконка владельца

Один Unity-объект собирается одним classic AssetBundle без запуска Addressables.
Его dependency closure (prefab, meshes, materials, textures и metadata) включён в
этот же bundle. Общие ассеты при необходимости дублируются: атомарность важнее
экономии копий. Файловые зависимости между публикуемыми bundles запрещены;
build gate вызывает `AssetBundleManifest.GetAllDependencies` и требует пустой
результат для каждого bundle. Общий `monoscripts` bundle и runtime-каталог
Addressables не существуют. C# остаётся в Player, а сериализованные компоненты
используют только стабильный content API выбранного runtime profile.

Внутренний Unity CAB-id также уникален и стабилен для каждого `type/id`.
Published filename может одинаково называться `payload.bundle`, но builder не
имеет права собирать разные объекты под одним `AssetBundleBuild.assetBundleName`:
иначе Unity считает их одним архивом и запрещает одновременную загрузку. Gate
проверяет, что два независимо собранных объекта можно держать открытыми вместе.

**Отдельного bundle или объекта каталога для иконок нет.** Если для объекта
нарисована авторская иконка, она находится внутри собственного payload рядом с
корнем `main` и экспортируется именованным entry `icon`. Например, bundle
`wear/skirt.anarchy` содержит prefab юбки, её metadata и её icon. Правка только
иконки юбки публикует следующую revision только `wear/skirt.anarchy`; ни одна
другая иконка, record или bundle не изменяется. `ItemIcons` разрешает icon через
record самого предмета и разделяет с его `main` один загруженный bundle handle.
Отсутствие авторской иконки допустимо: variant тогда не объявляет `iconAsset`, а
UI немедленно показывает стабильный emoji из `ItemCatalog` — например
`tool.spear → 🔱`, `item.bandage → 🩹` или glyph категории. Сборщик не создаёт
картинку-placeholder и не заставляет скачивать bundle ради fallback. Старые
bootstrap records с `metadata.iconPlaceholder=true` клиент трактует так же, как
отсутствующий `icon`, поэтому они не подавляют emoji и не требуют массовой
перепубликации.

Raw payload (`audio`, отдельный JSON) использует ту же модель record/blob, но
имеет `payloadType=file` и не открывается через Unity AssetBundle. Неотделимый
sidecar (например, запечённый `vis`-таймлайн голоса) входит attachment-ом в ту
же variant и object revision: сервер проверяет и переключает основной файл и
attachments одной транзакцией, а клиент не смешивает их из разных revisions. Логические
ссылки между объектами (например NPC носит `skirt.anarchy`) хранят только ID и не
создают bundle-зависимость.

Клиентский UI не является `ContentObject`: UXML/USS, `PanelSettings`, базовые
шрифты, небольшие общие emoji/icons и UI shaders/materials поставляются внутри
Player рядом с использующим их C#-кодом. Они обязаны работать до получения live
registry и не публикуются как `ui/*` bundles. Это не возвращает отдельный каталог
иконок предметов: иконка юбки, инструмента или другого игрового объекта по-прежнему
лежит только в payload своего владельца.
Иконка самого приложения также является частью Player, а не игрового контента:
`PlayerSettings` ссылается на `Assets/Resources/HexLive/UI/app_icon.png` по
стабильному GUID. Перенос UI в authoring/atomic root не имеет права удалять этот
файл — иначе build молча получает пустую стандартную иконку.

### §152.3 Сборка и атомарная публикация

CLI `content build --type <type> --id <id> --platform <platform>` находит
единственный authoring-root, собирает только его dependency closure, проверяет
`main`, обязательную metadata и, при наличии, авторский `icon`, запрещает внешние
dependencies, вычисляет SHA-256 и пишет candidate record. Команда не запускает
общий Addressables build и не трогает output, mtime или record других объектов.
Перед запуском Unity CLI проверяет все отслеживаемые Git LFS файлы и отказывается
собирать content, пока хотя бы один из них остаётся pointer stub вместо реальных
байтов. Временная metadata получает детерминированный GUID, выведенный из
`type/id`: повторная сборка неизменных входов обязана дать тот же SHA, поэтому её
повторная публикация остаётся server no-op.

Публикация выполняется административным CLI через SSH; публичного upload API нет.
Candidate сначала попадает в staging и целиком проверяется (размер, SHA и
обязательные платформы). Под межпроцессной блокировкой сервер повторно читает
текущий record, назначает следующую revision, переносит payload в адресуемый по
SHA immutable blob, пишет history и атомарно заменяет только record этого объекта.
Последним создаётся ровно одно событие журнала. Повреждённый или неполный
candidate current record не меняет; параллельные публикации одного ID
сериализуются.

Новый объект, необходимый симуляции, публикуется до отдельного обновления
`config/simdata`. При удалении сначала обновляется simdata, затем объект получает
новую revision со `state=retired`.

### §152.4 Постоянное хранилище и живой реестр

Контент хранится независимо от каталогов server/Player builds:

```text
/var/lib/hexlive/assets/
├── blobs/<sha256>
├── records/<type>/<id>.json
├── history/<type>/<id>/<revision>.json
├── changes/<registryRevision>.json
└── staging/
```

`records` содержит только текущее состояние каждого ID; `history` хранит
диагностику и источник точечного rollback. `registryRevision` — технический
монотонный номер журнала изменений, не content-set, не каталог и не версия игры.
Изменение юбки создаёт одну object revision, одно change event и только новые
платформенные blobs юбки. Bundle никогда не ссылается на реестр и после проверки
может загружаться из кэша без сети.

Для `wear` атомарная record также владеет серверным блоком
`metadata.simulation` по §154. Bundle publish сохраняет этот блок, если candidate
его явно не заменяет: визуальная пересборка не стирает настройки тепла, брони и
слотов. Общий SimData не является каталогом одежды; сервер получает effective
garments из live records поверх базового headless-моста §59.3.

Текущий `HexLive.Server` принимает `--asset-root` и предоставляет:

- `GET /api/assets/v1/index/{platform}/{runtimeProfile}` — компактный live index;
- тот же endpoint с `?after=<registryRevision>` — только изменённые/retired ID;
- `GET /api/assets/v1/objects/{type}/{id}?platform=…&profile=…` — один record;
- `POST /api/assets/v1/resolve` — records списка `type/id` текущего мира;
- `GET|HEAD /api/assets/v1/blobs/{sha256}` — immutable payload;
- `GET /api/assets/v1/objects/{type}/{id}/history` — административная история.

Index не имеет права молча укорачиваться. Активный объект, у которого нет
варианта для запрошенной пары `platform/runtimeProfile` (и нет совместимой
history-revision), возвращается в отдельном списке `platformMissing`, а не
пропадает: короткий index иначе неотличим от полного. Сервер при старте печатает
покрытие — число активных и retired объектов, все пары `platform/runtimeProfile`,
которые реестр публикует сейчас, и для каждой сколько объектов она загрузить не
может. Пара, которой нет в этом списке, не собрана ни для одного объекта.

Index поддерживает `ETag`, `If-None-Match` и compression. Blob отвечает
`Cache-Control: public,max-age=31536000,immutable`, поддерживает HEAD и byte
ranges; SHA в URL обязан совпадать с содержимым. API принимает только
валидированные type/id/SHA, но не произвольные пути. Kestrel публикуется через
HTTPS reverse proxy. Клиентский override —
`-hexlive-assets https://<host>/api/assets/v1`; для удалённого мира endpoint
автоматически выводится из его `ws/wss` адреса.
Боевой endpoint опубликован через TLS reverse proxy:
`wss://vmi3529459.contaboserver.net/watch`, а Asset API —
`https://vmi3529459.contaboserver.net/api/assets/v1`. Сохранённый прежний адрес
`ws://62.146.235.120:5123/watch` клиент нормализует в этот `wss` endpoint до
подключения, поэтому из него также выводится только `https` Asset API.
`PlayerSettings.insecureHttpOption=DevelopmentOnly` разрешает локальный
`http://localhost` контур в Editor/development build, но release Player не
может молча вернуться к публичному plain HTTP.

Live registry запускается ещё до выбора simulation-server, чтобы музыка меню
и bootstrap-контент не ждали подключения к миру. Поэтому endpoint без
`-hexlive-assets` по умолчанию является production Asset API, а не localhost;
локальный Asset API всегда задаётся явным CLI override. При смене игрового
сервера клиент повторно выводит Asset API, сбрасывает ETag/delta-состояние
предыдущего endpoint и не смешивает records независимых реестров.

### §152.5 Проверенный локальный кэш и сессионный pin

На старте клиент получает delta после последнего `registryRevision`, обновляет
только затронутые local records и фиксирует найденные revision/SHA до конца
процесса. Обязательные объекты текущего мира загружаются до снятия занавеса;
устаревшие уже закэшированные объекты обновляются фоном, незнакомые и пока не
нужные — лениво при первом использовании. Уже созданный в памяти объект не
заменяется посреди сессии.

```text
Application.persistentDataPath/HexLiveAssetCache/
├── blobs/<sha256>
├── records/<type>/<id>.json
├── registry-state.json
└── partial/<sha256>.part
```

Download пишется в `.part`, затем проверяются размер и SHA-256, после чего файл
атомарно переименовывается. Local record переключается только после проверки;
предыдущий blob остаётся fallback. Оборванная v2 не мешает использовать v1, а
недоступный API не мешает offline-старту с последней проверенной record. Лимит
кэша по умолчанию 12 GiB: LRU удаляет самые старые неактивные blobs, но никогда
не удаляет pinned blobs или payload текущих local records.

`blobs/<sha256>` обязан быть самостоятельным regular file. Symlink, junction или
иной `ReparsePoint` на build/worktree не считается verified cache даже при
совпадающем target; при promote legacy-ссылка удаляется и заменяется проверенным
`.part`. Удаление рабочего дерева поэтому не может превратить запись кэша в
`ERR_FILE_NOTFOUND` для FMOD или Unity.

Верификация SHA-256 выполняется при СКАЧИВАНИИ, но не при каждом запуске:
рядом с кэшем живёт персистентный стат-кэш `verified-blobs.json`
(sha → размер + mtime), и файл, не изменившийся со времени успешной проверки,
считается verified без пересчёта. Файл в `blobs/` появляется только через
verified promote (download пишет в `partial/` и переносится атомарно), поэтому
при первом запуске без стат-кэша существующий кэш штампуется целиком без
пересчёта. Blob контент-адресуем и после promote не перезаписывается;
LRU-доступ трогает только atime. Любое изменение размера или mtime возвращает
файл на полную проверку, повреждение содержимого без изменения метаданных
ловит сам `AssetBundle.LoadFromFileAsync`. До этого кэша тёплый клиент честно
хешировал сотни мегабайт за каждой шторкой («Проверяем …» на каждой вещи при
каждом входе).

Blob-запросы проходят через общую ограниченную очередь: одновременно работают
не более шести HTTP downloads независимо от числа prewarm-объектов. Временный
сетевой сбой повторяется до трёх раз с сохранением `.part` и продолжением через
Range. Тысячи голосов или attachments не должны создавать тысячи сокетов,
исчерпывать SSH/reverse-proxy соединения или превращать единичный reset в
непроверенную local record.

Index, resolve и потоковая загрузка blobs используют один долгоживущий
`System.Net.Http.HttpClient`; blobs читаются с `ResponseHeadersRead` прямо в
`.part`, без буферизации payload в памяти. `UnityWebRequest` в content path
запрещён: в Editor он может зависнуть до открытия сокета и не завершиться даже
по своему timeout, оставляя `RegistryReady=false` при исправном HTTPS API.
Timeout каждого запроса задаётся отдельным cancellation token, а HTTP-клиент
переиспользует ограниченный пул соединений.

`ContentAssetService` разрешает `type/id` через сессионный record, гарантирует
blob, вызывает `AssetBundle.LoadFromFileAsync`, загружает `main` либо `icon`,
кэширует bundle handles и reference counts и выгружает bundle только после
освобождения всех экземпляров. Runtime gameplay не использует
`Addressables.LoadAssetAsync`, resource locator или `Resources` fallback.
`Resources.Load` разрешён только для перечисленного выше стабильного клиентского
UI и bootstrap pipeline, но не как fallback игрового `ContentObject`.

Первый синхронный запрос к ещё не завершившемуся `LoadFromFileAsync` означает
`Loading`, а не отсутствие объекта. Presentation cache хранит это состояние и
повторяет установку visual на следующих кадрах; он не имеет права навсегда
зафиксировать первый `null` и заменить его кубом, цилиндром или другой
процедурной моделью. Состояния `Missing` и `Failed` терминальны и видимы как
ошибка конкретного `type/id`; единственный допустимый runtime fallback — прежний
проверенный blob того же объекта из кэша, а не геометрия другого ID.
⭐ Терминальность живёт ДО следующего здорового обновления реестра, а не до
конца сессии: один момент деградированного реестра (оффлайн-пин при недоступном
или повреждённом ответе) не имеет права навсегда оставить id без модели.
Здоровый refresh (`RegistryRefreshed` при пустом `LastError`) прощает
`Missing`/`Failed`, и следующий запрос честно начинает новую загрузку — ровно
одну на id за refresh, без покадрового шторма ретраев (неудача снова ставит
терминальный статус до следующего здорового refresh). Деградированный refresh
не прощает ничего: записи те же, повтор лишь продублировал бы ошибку в логе.

### §152.6 Реестр гардероба, prewarm, audio и simdata

`WardrobeCatalog` строится из metadata live records, а `WardrobeMeta` не читает
JSON рядом с Player. `ScenePrewarm` собирает ID реально присутствующих актёров,
одежды, волос, протезов, предметов, зданий и мобов и одним `resolve` передаёт их
в `ContentAssetService`. Иконки надетых, переносимых, лежащих и находящихся в
контейнерах объектов входят в тот же working-set prewarm и завершаются до снятия
loading curtain; это единое правило для одежды, еды, ресурсов, инструментов,
оружия, мебели, зданий и мобов, без особой ветки гардероба. Локальный `WorldState`
и удалённый `WorldSnapshot` перечисляют только реально присутствующих владельцев:
инвентари живых и трупов, надетое/в руках, содержимое контейнеров, лежащие объекты,
стройматериалы и живых мобов. Когда bundle нужного текущему миру объекта
открывается ради entry `main`, entry `icon`
немедленно читается из того же открытого `BundleState` и того же SHA. Отдельного
icon bundle, отдельной сборки или второго download нет; bundle объектов, которых
нет в текущем мире, ради иконок не открываются. Отсутствующая авторская иконка
завершает prewarm без download и сразу использует emoji. Неиспользуемая юбка не
скачивается только потому, что она существует в реестре. Loading UI показывает
фазу реестра, проверку кэша, скачивание с байтовым прогрессом и конкретную ошибку
объекта.

Каждый новый live snapshot повторяет working-set проход через идемпотентные
family caches. Поэтому появившиеся во время сессии мясо, инструмент или новая
вещь начинают одну загрузку owner bundle для `main + icon` сразу после попадания
в мир, а не при первом открытии инвентарной панели. Уже виденные ID остаются
дешёвыми cache hits; полный registry никогда не обходится ради картинок.

Тип prewarm-ключа всегда совпадает с владельцем payload: лежащая одежда остаётся
`wear/<id>`, а общий симуляционный id лежащего протеза разрешается в конкретный
левый/правый `prosthetic/<id>` тем же детерминированным правилом, что использует
его world view. Чисто симуляционные anchors (`build.site`, `building.hut_plan`,
вода, corpse/grave и отрезанная конечность), которые рисуются процедурно или
через уже загруженного владельца, не объявляются отсутствующими ContentObjects.

Скрафченная симуляцией одежда без собственного bundle (например
`clothing.leather_pants` — «Hide Pants», §54) разрешается через единственный
alias-слой `WearArtAliases`: sim id остаётся ключом кэшей и симуляции, а к
реестру уходит id вещи-донора (`wear/clothing.pants_biker`). Alias применяют ВСЕ
резолверы — надетый вид, ground drop, иконка и prewarm; без него id проваливался
в `object/<id>`, реестр честно отвечал «нет записи», и вещь была невидима на
теле, на земле и в инвентаре.

Любой физически видимый предмет, мебель, растение или моб, напротив, обязан
иметь собственный active record и renderable `main`. Кровать, шкаф, сушилка,
коллектор, верстак, тент, очаг, копьё, бутылка, пень и пальмовая деталь не могут
заимствовать mesh соседнего объекта или переходить на production-примитив.
Сборочный и runtime gate открывают payload, загружают `main` и требуют хотя бы
один непустой `MeshRenderer`/`SkinnedMeshRenderer`; наличие одного лишь config,
icon или пустого prefab публикацию не пропускает.

FMOD media получает raw files из того же registry/blob cache; WAV и его
attachment `vis` кэшируются и активируются как одна проверенная revision. `config/simdata`
— самостоятельный атомарный JSON-объект: локальная симуляция читает его через
API/кэш, удалённый authoritative server по-прежнему передаёт свой simdata в
handshake. Версии визуальных bundles к simdata не привязаны.

### §152.7 Минимальный Player и build gates

Player содержит код, stable content API, Unity/URP/FMOD runtime, стартовую сцену,
стабильные UXML/USS всех клиентских панелей, их небольшие общие UI-ресурсы,
минимальный выбор сервера/loading/progress/error, один компактный шрифт и
обязательные pipeline assets. В него не входят ImportedActors, игровые prefabs,
одежда/волосы/протезы и их иконки, предметы/здания/мобы, тяжёлый изменяемый
artwork, анимации, Addressables catalog или game bundles. Общие SFX, голоса,
музыка и FMOD banks входят в Player через три точных каталога StreamingAssets:
`HexLive/Sfx`, `HexLive/Music`, `FMODBanks`. Звук — часть стабильного клиента,
он не ждёт live-реестр и не публикуется как `audio/*` ContentObject.
Небольшие обязательные VFX (включая hit-blood) поставляются в
`Assets/Resources/HexLive/VFX`: бой и погода не имеют права менять вид или
исчезать из-за холодного content registry.
Общие карты ран, грязи, пота и бинтов по той же причине поставляются в
`Assets/Resources/HexLive/Decals`: они описывают состояние персонажа, а не
версию конкретной одежды, и должны быть доступны синхронно для каждого тела.

Шейдеры, которые код использует для runtime-generated мира через `Shader.Find`,
являются обязательной частью bootstrap pipeline, а не игровым content fallback.
Release gate проверяет, что `Universal Render Pipeline/Lit` и
`Universal Render Pipeline/Particles/Unlit` находятся в always-included
shaders; их stripping делает runtime-мир или дождевые частицы непригодными и
обязан останавливать сборку.

Player build никогда не запускает content build, собирается при полном отсутствии
bundle output, не создаёт `HexLiveContent` symlink/junction и падает, если
`BuildReport` находит игровой content asset. Gate также требует macOS `.app` не
более 850 MiB и суммарно `data.unity3d + StreamingAssets` не более 400 MiB:
лимит учитывает ~321 MiB обязательного аудио, но по-прежнему ловит случайное
попадание тяжёлых игровых prefabs и текстур.
Два transient `Resources/PerformanceTestRun*.json`, которые пакет Unity
Performance Testing создаёт только между pre/post-build callback, разрешены
точечно и не считаются игровым контентом. Префикс
`Assets/Resources/HexLive/UI/` разрешён только для стабильного клиентского UI,
`Assets/Resources/HexLive/VFX/` — для обязательных общих эффектов, а
`Assets/Resources/HexLive/Decals/` — для общих карт состояния тела/одежды; их
рост ограничен общим Player size gate. Для иных игровых Resources wildcard-
allowlist нет.
Стабильный стиль меню звука `Assets/Resources/HexLive/AudioSettings.uss`
разрешён отдельной точной записью в bootstrap allowlist.
Перед каждым release build локальная FMOD integration принудительно переводится
на готовые банки в `StreamingAssets/FMODBanks`, `ImportType=StreamingAssets`,
`BankLoadType=All`. Её временные `.bytes` stubs не могут оказаться среди packed
assets; исходные SFX/голоса и музыка читаются из Player-каталогов напрямую.
После миграции последнего runtime consumer пакет Addressables удаляется.

### §152.8 Приёмочные инварианты

Сборка и публикация `wear/skirt.anarchy` не меняют SHA, mtime, record или
revision других объектов; delta после неё содержит только юбку. Клиент с v1
скачивает только blob v2, клиент без юбки не скачивает её до необходимости,
загруженная v1 живёт до перезапуска, offline-клиент стартует с проверенной v1,
а rollback создаёт v3 с байтами v1. Для каждого bundle dependency list пуст.

Объект, собранный только для macOS, виден как пробел Windows: он попадает в
`platformMissing` индекса Windows, в список пропусков стартового покрытия и не
влияет на macOS. Retired-объект пробелом не считается.

Персонажи, одежда, волосы, протезы, предметы, здания и звук загружаются без
`Resources` и Addressables fallback; локальные UI и обязательные VFX запускаются
без asset API.
macOS и Windows Player собираются без предварительной сборки контента и без
доступного content output.

Staging-приёмка текущего мира дополнительно перечисляет весь working set из
snapshot и требует: каждый физический владелец разрешён live record-ом, его
`main` имеет renderable geometry, очередь загрузок завершилась до снятия шторки,
а в production-иерархии нет созданных вместо него `Cube`, `Sphere`, `Capsule`
или `Cylinder`. Добавление нового реально используемого ID без опубликованного
payload делает smoke красным, а не молча ухудшает картинку.
