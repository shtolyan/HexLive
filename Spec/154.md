## §154 Единый каталог контента и веб-админка (iteration 154)

Атомарный `wear/<id>` уже был источником визуального payload, но серверная
механика той же вещи оставалась строкой в общем `SimData/simdata.json`. Поэтому
новую одежду можно было опубликовать, но нельзя было безопасно включить в мир
одной операцией; удаление bundle, наоборот, оставляло симуляцию порождать
невидимый предмет. Один логический объект обязан иметь одну административную
карточку и один монотонный lifecycle.

### §154.1 Запись одежды — визуал и механика вместе

`records/wear/<id>.json` остаётся атомарной записью §152. В её `metadata`
зарезервирован владеющий сервером блок `simulation`:

```json
{
  "displayName": "Anarchy Skirt",
  "prototypeId": "clothing.skirt_anarchy",
  "layer": "Wear",
  "sex": "Female",
  "warmth": 0.05,
  "armor": 0.02,
  "thermalDelta": 0.0,
  "dressDurationTicks": 8,
  "capacity": 2,
  "covers": ["Pelvis", "LegL", "LegR"]
}
```

Имена enum совпадают с `WearLayer`, `GarmentSex` и `BodyPart`; неизвестное имя,
NaN/Infinity, отрицательная длительность или ёмкость и неполный блок
отклоняются до записи. `id` формы не редактируется: это ключ сейва и контента.
Новый bundle-publish, в candidate которого нет `metadata.simulation`, обязан
сохранить уже отредактированный сервером блок; сборка визуала не может стереть
баланс.

`SimData/simdata.json` остаётся базой совместимости и источником глобального
баланса, recipes, mobs, gear и world objects. Для wear сервер перед созданием
мира материализует effective SimData:

- active record с `simulation` добавляет/заменяет одну garment-строку;
- старая active record без блока берёт строку того же id из базовой SimData;
- новый active id без полного блока виден как `unconfigured`, но в симуляцию не
  попадает;
- retired record сохраняет последнюю корректную garment-строку с
  `retired:true`: существующие предметы/сейвы всё ещё имеют определение, но
  вещь исключена из всех случайных пулов и новых спавнов;
- если wear records ещё вообще нет, сервер работает на базовой SimData — это
  обязательная совместимость локального/первого запуска.

`config/simdata` не перечисляет версии bundles и не становится content release.
Effective JSON — производный runtime snapshot, а не второй редактируемый каталог.

### §154.2 Граница работающего мира

Мир фиксирует `registryRevision`, на которой был создан. Менять
`GarmentLibrary`, `ObjectDefinitions` и индексированный `DefinitionIdTable`
посреди тика запрещено: старый и новый клиент начали бы читать один wire-index
как разные id.

Сохранение карточки немедленно создаёт одну object revision и change event, но
работающий мир продолжает свою pinned revision. Действие «Применить каталог»:

1. строит и валидирует следующий effective SimData до остановки мира;
2. сохраняет текущий мир;
3. останавливает его tick thread и отключает viewers;
4. поднимает тот же seed/mode и восстанавливает тот же save с новым каталогом;
5. клиенты переподключаются и получают именно тот JSON, которым построен новый
   `DefinitionIdTable`.

Это не «новый мир»: save не архивируется и прогресс не теряется. Если сборка
effective каталога невалидна, текущий мир не трогается. В админке всегда видны
две цифры: live registry revision и pinned world revision; несовпадение помечено
как pending.

Добавленная active вещь участвует только в будущих выдачах после Apply. Retired
вещь после Apply больше не появляется, но уже надетая/лежащая остаётся рабочей.
Контекстный `POST /resolve` вправе вернуть последний совместимый payload retired
ID как `legacy`; он не попадает в публичный гардероб, но новый клиент может
нарисовать предмет из старого сейва. Blob удаляется только отдельным GC после
того, как history/сейвы перестали на него ссылаться.

### §154.3 Веб-админка

Существующая password/session-защищённая `/admin` получает переход в
`/admin/catalog`. Никаких CDN и upload API не добавляется. Каталог показывает:

- live revision и pinned revision мира;
- active/retired/unconfigured wear, число records каждого content type;
- число platform/profile variants, общий payload size и platform gaps;
- поиск по type/id/displayName, фильтры type/state и таблицу records;
- карточку `wear/<id>` с history, variant hashes/sizes и формой всех полей
  `simulation`;
- действия `retire`/`reactivate` с явным подтверждением и отдельное безопасное
  применение pending-каталога к текущему save.

Каждая POST-форма требует действующую admin session и передаёт
`expectedRevision`. Потерянное обновление отклоняется: администратор сначала
видит свежую карточку, а не затирает изменение другого publisher. GET ничего не
меняет; публичного изменения metadata по Asset API нет. HTML экранирует все
значения records и query, URL принимает только валидированные §152 type/id.

### §154.4 Атомарность и история

Редактирование metadata и state проходит под теми же process/file locks и тем
же transaction recovery, что bundle publish. Оно создаёт ровно:

- следующую object revision;
- immutable history record;
- один registry change;
- атомарную замену current record.

Variants и blobs при правке механики не копируются и не меняются. Повторное
сохранение идентичного значения — no-op. Retire не удаляет variants/blobs;
reactivate возвращает запись без повторной загрузки payload. SHA остаётся
адресом только байтов, а revision — монотонной версией всей карточки объекта.
