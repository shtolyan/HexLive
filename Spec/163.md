## §163 Agent Studio — локальные MCP-агенты, интеграции и отношения (iteration 163)

Agent Studio — отдельное приложение C#/Avalonia для macOS и Windows.
Маша является переносимым профилем, не особым способом управления.
Раздел задаёт целевой контракт; фактическое состояние реализации и проверки
ведутся в `Server/HexLive.AgentStudio/IMPLEMENTATION.md`. Наличие раздела не
означает, что изменения уже установлены на production.

### §163.1 Ядро и жизненный цикл

CLI и desktop используют `HexLive.AgentCore`, без зависимости от Unity.
Несколько профилей работают независимо. После запуска приложения все остановлены.
Сохранённые настройки каждого профиля содержат собственные ModelSelection и
VoiceSelection: например, Маша/Grok и Ника/DeepSeek или Codex могут работать
одновременно, с разными голосами и при необходимости разными интеграциями ключей.
Новый профиль не получает биографию Маши; использование существующего workspace
сохраняет его личность. Два профиля не используют одну папку памяти одновременно.
Подключение для чтения списка не вызывает LLM/TTS. Только явный запуск разрешает
модельные ходы (по умолчанию 30 секунд). Присутствие игрока не переключает агента.
Ответ игроку и автономное мышление используют один общий слот модели (#408,
§160). Новая реплика отменяет незавершённое автономное рассуждение, сохраняя
уже принятый приказ. Слот освобождается только после выхода вызова провайдера:
игнорирование отмены не разрешает второй одновременный вызов. Автономный ход
не начинается при ожидающем ответе игроку. Ожидание модели, озвучки или backoff не задерживает чтение
вопросов; единственный poller сохраняет интервал inbox 500 мс. У каждой ветки
собственные кэш справки и заменяемый read-only MCP-клиент; язык и разговорный
контекст передаются снимком конкретного запроса. Память, durable outbox, речевая
доставка и замена физического приказа сериализованы одним writer. Валидный новый
приказ игрока отменяет и делает недействительным ещё не зафиксированный автономный
результат. Ответ без приказа сохраняет выполняемое действие. Ошибка TTS сохраняет
готовый текст через существующий fallback, не запускает повторную модель.
Пауза мира отменяет текущий модельный запрос и запрещает новые платные операции.
Остановка отменяет запросы, не исполняет поздние ответы, освобождает attachment
и action lease (§160/§145). Аварийный fallback ограничен серверным TTL.
Переподключение допустимо лишь к тому же NPC в том же мире. Смерть, отзыв прав,
смена мира требуют нового выбора. Закрытие окна спрашивает про остановку/фон/отмену.
Полный выход останавливает всех. Один профиль нельзя открыть на запись дважды.

После durable commit решения физическая команда запускается ДО подготовки TTS
и публикации речи (#408). Медленная или недоступная озвучка не задерживает начало
действия; окончание TTS не отправляет приказ повторно. Во время синтеза общий
writer освобождён для inbox/history/heartbeat. Ошибка речи не откатывает действие.

Потеря фокуса или сворачивание Studio не останавливает heartbeat и не переводит
агента в сон: статус «Мир на паузе» определяется паузой мира. После сетевого
таймаута heartbeat, в том числе завершившегося как canceled task, рабочий цикл
восстанавливает MCP-сессию и attachment к тому же NPC/миру с задержкой 5 секунд.
HTTP 401 для уже установленной сессии допускает новое рукопожатие (сессия могла
истечь за время сна компьютера); HTTP 401 при новом initialize и HTTP 403
останавливают агент до исправления прав. Исходный RPC автоматически не повторяется,
истёкший экземпляр MCP-клиента больше не отправляет запросов (включая уже стоящие
в очереди действия); новое рукопожатие выполняет новый экземпляр после reconnect.
Отдельный read-only клиент справки заменяется при истечении сессии с освобождением
старого; только `read_spec` разрешена одна повторная попытка. Неуспех нового
рукопожатия возвращает обычный статус недоступной справки, без цикла повторов.
физические действия не воспроизводятся при reattach, незавершённый durable outbox
сохраняет существующую идемпотентную доставку. Явная остановка отменяет ожидание
и запросы и не запускает переподключение.

При сетевом разрыве/истечении attachment сервер сохраняет принятый inbox и
квитанции сообщений до 24 часов (не более 64 отключённых inbox в процессе).
Возобновление требует отдельный случайный `inboxResumeKey`, тот же NPC/поколение
мира и актуальные права MCP; одного имени профиля или attachmentId недостаточно.
Ключ выдаётся только владельцу attachment, не публикуется в /watch и не логируется.
Runtime держит его в памяти через сетевое переподключение. Это восстановление
после сна процесса, не гарантия при рестарте сервера или завершении приложения.
Обычная явная остановка не оставляет входящую очередь для другого агента.

### §163.2 Интеграции и доступ

Модель, каталог моделей и TTS — независимые адаптеры. Первый релиз: OpenAI API,
Grok API, Claude API, DeepSeek API, Codex через подписку ChatGPT; ElevenLabs либо
отсутствие TTS. Не переключать провайдера/способ оплаты автоматически. Каталог
моделей обновляется из API; показывать лишь поддерживаемые настройки мышления.
Внутренние рассуждения не отображаются, не сохраняются и не становятся памятью.
Проверка подключения не запускает генерацию. Проба голоса отдельно обозначена
как платная. Ключи защищены ОС, не экспортируются с профилем и не логируются.
Приложение использует /mcp, игра /watch. Основной вход Studio — адрес и тот же
игровой Bearer-токен, без кодов и запросов одобрения; сервер проверяет права при
каждом вызове. Обычному пользователю доступны назначенные NPC, admin-права
проверяются отдельно. Сервер передаёт world ID, паузу и идентичность отправителя.
Сервер не владеет личностью или долговременной памятью агента.

Studio читает `HexLive.RemoteClientId` собранной игры автоматически (macOS:
`com.juilcylove.hexgirls`; Windows: `HKCU/Software/JuicyLove/HexLive`). Настройки
Editor не используются. При отсутствии ID показать инструкцию запустить игру,
не генерировать новую личность. ID сохраняется в подключении и передаётся
`X-HexLive-Client-Id`, как в /watch. MCP сам не создаёт назначений персонажей.
Сессия выдаётся сервером, привязана к player ID и миру, живёт до пяти минут без
обращений; каждый запрос проверяет игровой токен и текущие назначения.
Это существующая доверительная модель игрового shared token, а не персональная
криптографическая учётная запись: знающий общий токен и чужой ID не должен
считаться изолированным от этого игрока. Не раздавать общий токен недоверенным.

Legacy pairing сохранён для старых клиентов, но Studio его не вызывает.
Подтверждение legacy подключения ограничено двумя минутами: случайный восьмизначный
hex-код подтверждается авторизованным владельцем в игре, отдельный случайный
секрет позволяет приложению получить результат. Не более четырёх новых запросов
с одного сетевого источника в минуту и восьми попыток кода на запрос.
Сервер сохраняет только хеш постоянного credential. Пользовательская MCP-сессия
выдаётся сервером, привязана к credential и world ID; подставленный session ID
не даёт доступа к attachment или лизу. Список NPC фильтруется по актуальным
назначениям, read_events пользователя требует конкретного доступного npcId.
Проверка attachment не продлевает TTL: потерявший права агент не удерживает тело.
Административный доступ остаётся отдельным контуром.
Единое скрытое поле принимает игровой токен; прежний глобальный hexmcp-токен
также поддерживается без импорта игровой личности и сохраняет широкие права.
Это не голосовое разрешение администратора §161. До записи в системное хранилище
проверяются world_status и list_colonists без attachment или платных запросов.
Неуспешная проверка не заменяет сохранённые credentials. Административное
и обычное подключения могут иметь разные имена для одного endpoint;
каждый профиль выбирает своё подключение.

Начало и опрос pairing доступны без credential как ограниченные MCP-вызовы
request_agent_pairing/displayName и poll_agent_pairing/pairingId,pollSecret.
Остальные вызовы требуют авторизации; unauthenticated batch не поддерживается.
Игра подтверждает запрос через optional /watch frames 24 AgentPairingInput и
25 AgentPairingResult (строки id/code, bool approve; максимум 512 байт, строгий
UTF-8). Ответ передаёт имя приложения и результат, не credential. Старым
клиентам кадры не посылаются без их запроса. Старые версии игры предоставляли
подтверждение кода id:code в меню Escape. В текущем клиенте этот устаревший блок
удалён (bug #420): подключение настраивается в Studio через игровой токен и
существующий client ID. Серверный legacy-протокол остаётся совместимым со старыми
клиентами; новая форма подключения Studio не вызывает pairing.

### §163.3 Переносимая память и отношения

Цель хранит стабильную StartedRevision — номер операции set, в отличие от Revision,
меняющейся при каждой паузе/возобновлении. Это сохраняет выбранные справки для той
же задачи во время восстановления; новый set даже с тем же текстом очищает их.
Старые сохранения без StartedRevision используют текущую Revision до первой смены
статуса. Оптимистическая проверка изменений по Revision остаётся прежней.

Для подготовки плана read-only цикл допускает `spec.read(section, offset)`,
`skills.list` и `skills.read(id)` рядом с поиском памяти. Навыки сбора/доставки,
подарка и кровати версионированы в `AgentPrompts/skills.json`; это процедуры,
а дополнительные навыки профиля читаются из `MASHA_HOME/skills/catalog.json`.
Локальный каталог ограничен 64 записями/256 КиБ и не поддерживает ссылки на файлы.
Без `status: validated` навык остаётся кандидатом и не входит в справку модели.
Для validated обязательны положительная version, title, procedure и validationReport
(путь/идентификатор отчёта сценарной проверки, заполняемый разработчиком).
Это декларация проверившего разработчика, не автоматическое доказательство теста.
Замена встроенного навыка требует большей версии; новый профиль не наследует
локальные навыки другого профиля. Чтение обновляется при каждом запросе справки.
Навыки не дают новых полномочий и не заменяют фактические рецепты/наблюдения. Источник
содержит тип, имя, offset и SHA-256 прочитанного фрагмента. Пагинация сохраняет
реальный nextOffset. Общий бюджет чтения — 24000 символов, переданного контекста
— 16000, до двух операций за раунд и трёх дополнительных раундов. Промежуточные
запросы не фиксируют речь, отношения, цель или очередь команд. Техническая трасса
сохраняет использованные ID источников и объём чтения без внутренних рассуждений.

`describe_colonist` передаёт численные собственные нужды отдельными именованными
полями (Energy, Stamina и Breath не объединяются) и статус исполняемого действия.
`read_recipes` читает действующий RecipeCatalog, включая настроенные в мире
ингредиенты, станцию и работу, с идентификатором версии содержимого. Это публичные
правила мира, не доступ к чужому инвентарю. `recipes.read` доступен в справочных
раундах. Модель может выбирать штатный `transfer_inventory`: Give следует §153,
Take — §128; допуск и проверка предмета остаются на сервере.

Видимые стройки в `visibleItems` содержат product, авторитетную ведомость,
доставленное количество, общий и текущий дефицит стадии, необходимость молотка.
`hammerRequiredFor` уточняет фазу: finishingWork для требующего молоток продукта,
none для HandBuilt. `materialDeliveryRequiresHammer=false`: по §54 доставка
материалов до полной оплаты доступна без молотка; это не обещание допуска Build
при других препятствиях и не подтверждение наличия нужного инструмента.
Чтение не расширяет видимость и не обновляет личную память. `read_build_catalog`
(справочная операция `build.read`) даёт каталог мебели, требования и предварительную ведомость из того же сборщика,
который создаёт площадку; при расчёте продолжения приоритет у конкретной стройки.

Редактируемые SOUL.md/USER.md не перезаписываются генератором. Сохранение имеет
проверку версии, резервную копию и историю; новая редакция действует со следующего
хода. Сохраняются импорт iPhone, старые острова и существующие прозвища.
Экспорт/импорт — архив под паролем без credentials, только для остановленного
профиля и без молчаливой замены. Облачная синхронизация не входит в первый релиз.

Модель обновляет до трёх memoryUpserts суммарно: ключи user: — сведения о
собеседнике, core: — биографическая память между мирами; world: и остальные
ключи, включая устаревший self:, остаются памятью текущего мира. SOUL.md —
авторское описание личности, модель не дописывает его через memoryUpserts.
Временные слоты/нужды/индексы и фаза задачи берутся из текущего наблюдения и плана,
а не закрепляются как постоянные выводы. Правила требуют актуальной справки. Это факты и краткие выводы, не скрытые
рассуждения, идентификаторы аккаунтов или новые системные полномочия.
USER.md/MEMORY.md и заметки миров/дней получают выделенную секцию
agent-studio:notes. При миграции точная копия секции вне маркеров удаляется только
после резервирования; отличающийся ручной текст сохраняется. Новый USER.md не
получает одновременно обычную и служебную копии. Редактор USER.md/MEMORY.md/SOUL.md
записывает надёжную операцию before/after вместе с документом под общей блокировкой.
Перед следующим контекстом или сохранением ядро однократно применяет изменения
фактов; удалённые значения не восстанавливаются seed-инициализацией или старым
memoryUpsert. Восстановление через историю является новой явной редакцией.
USER.md относится к подтверждённому основному собеседнику либо отдельной legacy-записи,
не ко всем людям сразу. Явная правка процентов в USER.md меняет соответствующие
числа (знакомство/доверие 0..100%, симпатия -100..100%); удаление строки процентов
не обнуляет отношения. Неверные числа отклоняются до сохранения. Предыдущий документ
и состояние перед применением редакции резервируются. Повторный turnId не обновляет
память второй раз. Сведения о собеседнике включаются
в ограниченный контекст отдельно от начального фрагмента Markdown.

Старые model-self остаются в архивном состоянии и показываются в
`memory/legacy-self.md` с пометкой о необходимости проверки. Они больше не
подаются отдельным блоком личности. Старый управляемый раздел SOUL.md удаляется
только после атомарной записи полного исходного документа в `memory/legacy-soul/`
и `.history`; весь текст вне маркеров сохраняется дословно. Эти архивные файлы
доступны в браузере памяти, но не участвуют в автоматическом recall. Неизвестные
мир и актуальность не выдумываются. Миграция повторяема после сбоя; ошибка
резервирования сохраняет исходную душу. Ожидающие авторские правки применяются
до миграции, удалённый старый self-факт не возвращается повторным self-upsert.

Отношения принадлежат паре агент/собеседник. Знакомство и доверие 0..1,
симпатия -1..1; старые положительные значения сохраняются численно.
Знакомство +0.02 только при новой значимой информации; доверие +0.03/-0.05,
симпатия +0.02/-0.05, серьёзное негативное воздействие -0.10/-0.10.
Сохранённые отношения не пересчитываются: новый баланс действует только на новые
оценки. Резкое отношение не восстанавливается одним ласковым словом; положительные
шаги остаются прежними. Диагностика фиксирует числа и фактические дельты после commit.
Допустимо отсутствие любых изменений. Знакомство не падает из-за ссоры.
Оценка применяется один раз к пакету новых сообщений; повторная доставка и
heartbeat не дают прибавок. Social в симуляции остаётся отдельным показателем.
В каждом промпте есть обязательный необрезаемый блок отношений. Удаляются
только известные старые безусловные инструкции про дорогой голос после backup,
не реальные воспоминания. Симпатия определяет теплоту, доверие — готовность
полагаться на советы, знакомство — узнавание. Допустимы плюс, минус и ноль;
несогласие не равно оскорблению, возможна реабилитация отношений.
Агент может назвать голос; имя и причина сохраняются без смены аккаунта/NPC.
Нет биометрической идентификации. Связь аккаунтов разных серверов подтверждается
пользователем. Игра и Studio показывают одинаковое публичное представление.
Просмотр служебных отношений read-only; явная авторская редакция USER.md описана выше.
Служебные отношения зашифрованы с проверкой целостности; это защита
от простой подмены, не античит против владельца машины.

### §163.3a Авторский голос, собеседники и игровое время

Общее ядро собирает запрос через AgentPromptBuilder. Версионированный авторский
DialogueStyleId (`masha-sharp-v1` для Маши) задаёт разговорную резкость, естественный
мат и конкретные подколы. Симпатия меняет смысл колкости от отталкивания до близости,
доверие — опору на совет, знакомство — узнавание. Два детерминированно выбранных
одобренных примера являются образцами речи, не воспоминаниями. Авторский профиль
не изменяется memoryUpserts; другие персонажи не наследуют его автоматически.
Блоки стиля, актуальных отношений и игрового времени не обрезаются бюджетом recall.
relationshipAssessment оценивает смысл новых сообщений, не грубость собственной
реплики. VoiceRelationship применяет шаги §163.3 отдельно от reaction/Social.
Сервер передаёт идентификатор собеседника из авторизованного подключения; отношения,
user-факты и последние 12 строк диалога изолированы по серверу/собеседнику и
сохраняются вместе с результатом хода. Полный локальный архив разговоров и доступных событий ведётся по §165; последние 12 строк остаются кратким контекстом. Повторы сообщений
не меняют отношения повторно, даже после восстановления outbox. Старый положительный
bond сохраняется численно и переносится только подтверждённому владельцу;
непривязанные импортированные данные не выдаются за отношения с новым человеком.

Время с общения/наблюдаемого ухода определяется тиками того же мира и серверным
dayLengthTicks. Пауза добавляет ноль; ускорение учитывается фактическим ходом мира.
Молчание не равно отсутствию. Смена мира/откат/неизвестный tick не получают UTC-fallback.
UTC остаётся служебным временем хранения, соединений и таймаутов. Голосовой ход
снимает ожидание приветствия один раз; heartbeat не меняет отношения.

Речь агента ограничена 600 символами, обычно 1–3 фразы; намерение — 240.
Озвучка до 60 секунд и 6 МиБ, при ошибке сохраняется текст. Действия подтверждаются
игрой, литературные ремарки не считаются выполненными действиями и не озвучиваются.
Реальная приёмка — 30 сценариев по два прогона в тестовой памяти, без управления
живым миром: >=90% соответствия стилю/отношениям и отсутствие критических ошибок.

### §163.3b Одна сохраняемая цель агента

Профиль хранит одну явную долгосрочную цель в существующем `.state/state.json`,
отдельно от краткого intentSummary и фактического действия тела. Цель включает
текст (до 600 символов), статус, причину изменения (до 240), монотонную версию,
мир и NPC назначения. Перезапуск и переподключение сохраняют её. Модель может
назначить/заменить (set), приостановить (pause), возобновить (resume), завершить
(complete) или снять (clear) цель; null/отсутствующее objectiveUpdate ничего не
меняет. Переходы active↔paused, active/paused→completed, active/paused/completed→canceled;
set назначает active из любого состояния. Resume/complete требуют исходный мир
и NPC; в другом теле нужна новая осознанная оценка и set. Текст прежней цели
сохраняется при смене статуса. Старая память и старые outbox-решения совместимы.
Pause/clear разрешены и в другом мире/теле для явного пересмотра; clear оставляет
текст отменённой цели как историю, а не удаляет его.

Блок цели обязателен в ограниченном prompt, независимо от рейтинга воспоминаний.
Модель выбирает конкретные безопасные шаги, учитывает выживание и приостанавливает
цель с причиной, если нужно; complete требует наблюдаемого результата, а не
подтверждения приёма команды. Отдельного автоматического исполнителя цели нет.
Markdown мира показывает сгенерированное состояние той же цели, не вторую базу.

Цель и AppliedTurnIds записываются одним существующим commit памяти; повтор
durable turn не меняет версию повторно. Prompt и версия берутся из одного снимка.
Перед outbox позднее решение, меняющее цель или запускающее действие по старой
версии, отклоняется без записи и подтверждения inbox: вопрос остаётся для повтора.
Изменение цели ответом игроку отменяет устаревшее параллельное решение автономии,
даже без нового физического action. Read-only query_known_objects сохраняет тот
же снимок/версию на дополнительном модельном запросе.

### §163.3c Протокол исполняемого плана (#409)

План привязан к миру, NPC и версии цели; новая редакция получает новый ID от
контроллера. Курсор шага и версия состояния независимы от версии цели.
Физическое продолжение долгосрочной цели задаётся очередью, в том числе после
завершения предыдущего сегмента; допустим сегмент из одного шага. Промпт отличает
это от одиночного action и разрешает read-only разведку query_known_objects.
Если провайдер всё же выдаёт одиночный физический action для продолжения
активной цели после завершённого/отказавшего сегмента, контроллер преобразует
его в один сохраняемый шаг до проверки и commit. Аргументы и смысл действия
не меняются. Это не заменяет активную/неопределённую очередь: без явного
executionPlanUpdate такая подмена отклоняется. Пауза/снятие цели, справочный
поиск и действия вне активной цели сохраняют прежнюю семантику.
Первая часть протокола поддерживает ограниченную последовательность до 64 команд;
ветвления, наблюдения и навыки подключаются отдельно. Аргументы каждого шага
проверяются по актуальному MCP-каталогу перед отправкой, NPC задаёт attachment.
Шаг может содержать численное условие `condition` по свежему `describe_colonist`:
`path`, `operator` (gte/lte), `value`, `onFalseStepId`. Разрешены только
inventorySummary.freeSlots, bodyNeeds.energy.value/stamina.value/hunger/thirst
и restReadiness.adrenalineTicksRemaining/idleRestCooldownTicksRemaining.
При ложном условии курсор сохраняется на указанном последующем шаге; пустая цель
ветки ставит паузу ConditionsNotMet. Отсутствующее наблюдение — ошибка, не ноль.
Переходы только вперёд, неизвестные/обратные переходы отклоняются. Проверка
выполняется до отправки; квитанция уже отправленной команды всегда сверяется
независимо от условия. Старые шаги без condition исполняются как прежде.
Планы с условиями сохраняются с schemaVersion=2: старая Studio должна отвергнуть
неподдерживаемую версию, а не исполнить команды, проигнорировав условия.

Для ограниченного повторения одного действия шаг может содержать repeat=1..64
(по умолчанию 1). Суммарно не более 256 отправок в плане. Это, например,
несколько изготовлений по известному рецепту с неизменными аргументами; не
автоматический подбор нового objectId. Перед каждой итерацией заново читаются
наблюдения и условие. Каждая получает собственные commandId/sequence; лишь её
completed увеличивает сохраняемый счётчик Iteration. Сбой прерывает цикл,
reconnect сверяет текущую итерацию, отмена запрещает оставшиеся повторения.
Такие планы используют schemaVersion=3; предыдущая Studio их не исполняет.

`describe_colonist.restReadiness` отдаёт результат того же телесного гейта
ручного сна, что и native executor: sleepBodyReady/sleepBodyBlockReason,
оставшиеся тики адреналина и кулдауна праздного отдыха, число воспринимаемых
угроз. Это read-only состояние привязанного NPC; sleepSpaceChecked=false:
геометрия места и путь проверяются только штатной командой. Ненулевой адреналин
не исчезает от смены кровати. Явный ручной GroundSit допускает IdleRest fallback
без разрешения самовольного Idle (§137).

`rest_until` — ограниченный отдых внутри `execute_agent_command`: need=Energy
задаёт штатный GroundSleep, need=Stamina — GroundSit, target в (0,1]. В отличие
от бессрочного ручного сна §121, сервер завершает именно эту команду после
достижения заданного показателя во время соответствующего отдыха и штатного
Stop. Порог хранится вместе с активной квитанцией; reconnect не продлевает сон
и не создаёт повтор. Прерывание/потеря контроля остаются failed, не успехом.

Диагностика связывает хеши plan/step/command, номер команды, версию цели и
плана с квитанцией и её машинной причиной. Наблюдения до/после включают отдельные
Energy/Stamina/Hunger/Thirst. Каждый запрос модели (включая справочные раунды)
получает latency и известный transport usage. Нет данных о токенах — null, не 0;
ошибочный/прерванный ответ не выдаёт придуманного usage. Metadata transport не
принимается из решения модели и не входит в его сохраняемый JSON-контракт.
Codex CLI получает JSON Schema через штатный `--output-schema`, отдельно от
текстовых инструкций. Файл создаётся в приватном временном каталоге запроса и
удаляется вместе с ним; ответ по-прежнему проходит локальную строгую проверку.
В закрытой транспортной схеме Codex открытые MCP arguments представлены списком
пар name/value (скалярные значения), затем преобразуются обратно в объект перед
проверкой игрового контракта. Повторные имена и вложенные значения отклоняются;
игровой протокол и сохраняемые планы от этой адаптации не меняются.
Grok получает исходную схему решения в response_format.json_schema (strict=true),
а не только json_object. Код причины и ID шага ограничены машинным форматом.
Локальная семантическая проверка обязательна и после ответа провайдера.

В памяти цели сохраняются последние 64 подтверждённые команды с их аргументами,
ID/номером квитанции и привязкой к миру/NPC. Они фиксируются атомарно с курсором,
переживают замену сегмента и restart; новая цель или clear очищают этот прогресс.
В пределах лимита 64 записей защищаются последние подтверждённые Build-команды
для восьми разных площадок: длинная серия PickUp не вытесняет все ID стройки.
Их краткий список передаётся отдельно от последних восьми обычных квитанций.
Это исторические цели команд, не доказательство текущего типа объекта или готовности:
перед продолжением модель сверяет construction.product и ведомость по свежему миру.
Пропущенная по условию команда не считается выполненной. Промпт показывает
последние подтверждённые действия и следующие шаги в пределах общего бюджета,
чтобы завершившая доставку модель не начинала её заново из-за отсутствия истории.
В пределах одной активной версии цели recall запоминает последние восемь успешно
прочитанных справочных запросов, кроме одноразового inventory.drop.read: его индекс
и место относятся к конкретному состоянию инвентаря. Перед следующим решением
recall обновляет выбранные справки без LLM, начиная с последних использованных,
в общем окне до 8 секунд и до 12000 символов, оставляя бюджет для новых чтений.
Свежие версии/источники входят в прежние общие пределы 24000/16000 символов;
модель использует уже переданные readSources без повторного запроса тех же страниц.
Старый текст не служит
fallback при ошибке. Смена цели/мира/NPC сбрасывает список; restart перечитывает
справку обычным путём. Это сокращает повторные модельные раунды для того же навыка.
Поиск query_known_objects выполняется внутри этого же справочного цикла: его
второй модельный запрос сохраняет уже прочитанные источники, а дополнительные
memoryRequests обрабатываются до фиксации итогового решения. Результат поиска
остаётся в наблюдениях последующих справочных раундов. Лимит поиска прежний —
один запрос за ход; лимит справочных раундов и общий бюджет чтения не увеличены.
Общий предел recall для активной цели или обращения к игровым справкам —
300 секунд от начала хода; для обычного поиска личной памяти остаётся 120.
Предел продлевается один раз, не на каждом раунде. Отмена attachment/хода
по-прежнему прерывает работу сразу; это не разрешение дополнительных раундов.
Противоречивый ответ с action и executionPlanUpdate одновременно не исполняется
и не озвучивается. Справочные чтения и исправления имеют отдельные счётчики:
до трёх раундов чтения и до трёх исправлений, всего не более семи ответов recall
(плюс прежний один дополнительный ответ после query_known_objects). Поэтому ошибка
финального плана после трёх чтений ещё может быть исправлена. Лимиты символов и
общий таймаут не растут; четвёртое исправление запрещено. Тот же модельный поток
получает код ошибки и выбирает одну форму; исчерпание бюджета завершает ход ошибкой.
`complete` не совмещается с новым action или изменением очереди, даже если
предыдущий сегмент уже закончен. Этот конфликт исправляется в том же ограниченном
цикле до речи и записи состояния; сама запись также проверяет инвариант. Нельзя
одновременно заказать выгрузку и объявить её выполненной: завершение цели требует
следующего наблюдения подтверждённого результата.
Перед `transfer_inventory` в направлении Give справочный контур требует
актуальный источник `spec:153` в переданном модели контексте. Один пересказ навыка
не заменяет правила подарка. При отсутствии источника модель в оставшихся
раундах получает GiftRulesNotRead и запрашивает `spec.read`; до этого ни речь,
ни передача не исполняются. Исчерпание бюджета отвергает ход. Это проверка
подготовки решения, а не дополнительное разрешение на передачу.
Итоговый ответ также проходит немутирующий preflight того же хранилища, которое
затем фиксирует цель и очередь. Ошибки переходов цели/очереди возвращаются модели
для ограниченного исправления до публикации; например, pause вместе с новой
очередью сна не исполняется. Сон может быть шагом активной исходной цели.
Конфликт ревизий, отмена, ошибки доступа, транспорта и диска не считаются
ошибками решения и не повторяются этим механизмом. При commit проверка остаётся
обязательной, поскольку состояние могло измениться после preflight.
Та же ограниченная попытка исправления применяется к InvalidExecutionPlanUpdate
и InvalidExecutionCondition: модель получает правила идентификаторов и переходов,
команды до успешной проверки не отправляются. Ошибки транспорта и авторизации
не превращаются в такие повторные модельные запросы.
Исправляющий запрос содержит также отвергнутый итоговый JSON (до 32768 символов)
как данные: модель исправляет конкретный ответ, а не угадывает его заново.
Постоянная диагностика сохраняет только код ошибки, без этого сырого JSON.
Ошибка передаётся отдельным controller decisionRepair, а не результатом поиска
памяти. Для неверного перехода указываются ID ошибочного шага, его цель и список
существующих последующих шагов. Источники памяти и справок при этом сохраняются.

После фактического получения обязательных правил подарка требование GiftRulesNotRead
снимается из следующего контекста: оно не должно запускать повторное чтение той
же страницы. Неполный ответ провайдера IncompleteModelResponse не исполняется;
контроллер может запросить полный JSON в общем лимите трёх исправлений и том же
таймауте. Исчерпание лимита остаётся ошибкой, а не успешным решением.

Если rest_until получает уже достигнутый target, сервер завершает шаг как
RestTargetReached без поиска места для восстановления. Обычный Stop через
ту же командную шину сохраняет проверку актёра и очистку прежнего действия.
Квитанция и идентификатор остаются идемпотентными; повтор не посылает Stop снова.

`describe_colonist.recentGiftResults` передаёт до восьми последних GiftGiven
самой колонистки из ограниченного SimulationEventBuffer: sequence, tick, type
и details с фактическим адресатом/предметом/реакцией. Чужие действия не попадают
в поле. partialHistory=true: отсутствие записи после вытеснения или restart
не доказывает отсутствия подарка. Агент сопоставляет эту ленту с сохранёнными
completed квитанциями и инвентарём. Голод адресата после вручения не означает
невыполненный подарок; употребление вещи — отдельное действие.

Справочный `inventory.drop.read` привязывает npcId к телу attachment и проверяет
один carried-экземпляр по актуальному индексу и definitionId. Серверный
`read_inventory_drop` не берёт lease и не меняет мир/инвентарь. Штатный
GroundItemPlacement по умолчанию проверяет текущую точку и до 18 подходов в
радиусе двух тайлов (всего до 19 начал поиска). После исчерпания локальной области
можно запросить approachRadiusTiles от 1 до 6: максимум 127 начал поиска.
Каждый поиск допускает Drop в соседнем кольце, то есть область до семи тайлов
от исходной при максимальном радиусе (169 гексов). Возвращаются canDropHere,
approach, checkedOrigins, found/NoNearbyDropSpot. Это геометрическая проверка,
не маршрут и не резервирование: после перемещения требуется новая проверка.
Подход выбирается только на внутреннем узле, принадлежащем одному тайлу:
общий граничный узел может отнести NPC к соседнему тайлу после move_to и тем
самым изменить область последующего Drop.
Чужой NPC закрыт обычным player scope; устаревший индекс возвращает
StaleInventoryItem без поиска. Штатные радиусы и правила Drop не меняются.

Перед отправкой сохраняется состояние `sending` с идентификатором команды,
однозначно связанным с планом и шагом. `accepted` не двигает курсор. Только
подтверждённый исход конкретной команды `completed` завершает шаг; ожидание,
пустая очередь NPC или слова модели не заменяют такое подтверждение. Поздний
ответ предыдущего шага не применяется к следующему. Ошибка приостанавливает
план, а повторное принятие того же результата не изменяет состояние.
После подтверждённого `failed` модель может заменить план для той же цели,
а машинная причина серверной квитанции сохраняется в Command.Reason и следующем
контексте решения. Она ограничена форматом кода (до 96 символов), а не произвольным
серверным текстом. Повтор того же отказавшего шага требует новых оснований.

Модель продолжает работу,
опираясь на свежие наблюдения: сбой шага не требует заново назначать цель.
Новый план получает новые идентификаторы; это не автоматический повтор команды.
`sending`, `accepted` и `unknown` блокируют замену до сверки исхода либо явной
отмены. Диалог сам по себе сбой не снимает.

После переподключения `sending`/`accepted` становятся неопределённым исходом
и сверяются по прежним ID. Временная потеря ответа запускает до трёх сверок с
интервалом не менее двух секунд без повторной отправки и без вызова модели.
Lease не освобождается посреди такой сверки. Подтверждённое completed продолжает
очередь автоматически только для паузы CommandOutcomeUnknown и всё ещё активной
цели; пауза игрока или критического события этим не снимается.

`resume` допустим только для paused очереди без команды, привязанной к текущей
активной цели и персонажу. После failed требуется исправленная замена очереди;
попытка resume такого шага возвращается модели как InvalidExecutionPlanTransition
до commit. Завершённая очередь не отменяется повторно.

При `unknown` команда не отправляется повторно. Даже обычный resume запрещён,
пока исход не сверён. Питьё и еда планируются до длинных рабочих сегментов по текущим нуждам и
актуальным возможностям предметов, как шаги активной цели. Сон/отдых сохраняют курсор; завершение действовавшей
команды во время явной паузы не возобновляет оставшиеся шаги само. Явная отмена
терминальна и не означает откат уже совершённого действия. Завершение очереди
само по себе не переводит долгосрочную цель в completed.
Обратная проверка тоже обязательна: complete цели при active/paused очереди
запрещён до commit. Сбой последней выгрузки не превращается в успех по словам
модели. Recall просит исправить такой ответ в оставшемся бюджете; снятие задачи
через clear остаётся доступным и не называется успешным выполнением.

`executionPlanUpdate` устанавливает/заменяет, приостанавливает, возобновляет
или отменяет очередь; null не меняет её. Временная опасность при действующей цели
оформляется pause очереди и отдельным экстренным action, без pause самой цели.
После известного исхода этого action Studio удерживает lease активной цели,
если очередь приостановлена без неопределённой команды: встроенный AI не начинает
другую работу между решениями. После устранения причины модель явно возобновляет
или заменяет очередь. Пауза самой цели означает прекращение её исполнения и
освобождение управления; отключение Studio также освобождает lease. Неизвестный
исход команды по-прежнему требует сверки, а не повторной отправки.
Установка плана, цель и AppliedTurnIds
фиксируются в одной транзакции `.state/state.json`. Snapshot промпта содержит
ID и версию плана: позднее решение не заменяет уже продвинувшийся план.
Подготовка отправки и каждый исход сохраняются под тем же lock памяти до
перехода к внешнему действию. Ошибка записи запрещает дальнейшую отправку
из этого экземпляра store до перезагрузки; неизвестный исход не откатывается
в состояние «можно отправить». Смена/снятие цели отменяет старую очередь,
обычный разговор сохраняет курсор. Старые архивы без плана совместимы.

Runtime исполняет последовательность через `execute_agent_command` и читает
`read_agent_command`: номер записывается в checkpoint до отправки. Шаги переходят
без модели и TTS, лиз удерживается между ними и продлевается во время ожидания.
Пока очередь выполняется, heartbeat программный. Завершение/сбой запрашивает
новое решение; критическое событие сначала приостанавливает очередь. Обычная
реплика не отменяет её. После завершённого сегмента активной цели runtime
сохраняет лиз и продлевает его каждые девять секунд, пока модель выбирает
продолжение. Встроенный ИИ не получает управление между сегментами. Новая
очередь принимает тот же лиз; пауза/завершение цели, пауза мира и detach
освобождают его. При аварии действует прежний TTL, бессрочной аренды нет.
При неизвестном исходе выполняется сверка квитанции,
никогда повторная отправка; после явной паузы продолжение требует resume.
Перед принятием нового плана проверяются серверные capabilities и схемы шагов.
Сценарии адаптивного сбора/строительства и навыки остаются отдельной приёмкой.
Модельный стенд использует тот же `KnowledgeAwareAgentProviders`, что CLI и
Studio: автоматические актуальные выдержки `read_spec` по нуждам тела добавляются
до решения. Проверка обходящего этот слой провайдера не является приёмкой
полной конфигурации приложения. Отчёт записывает `providerComposition`; старые
результаты без этого поля и новые прогоны не объединяются в одну матрицу.

### §163.4 Интерфейс и приёмка

### Техническая диагностика исполнения (#409)

Каждый runtime CLI/Studio постоянно пишет локальный JSONL в
`StateDirectory/diagnostics/events.jsonl`: schemaVersion, sessionId, sequence,
UTC, хешированные profile/world/turn, NPC, тип события, код результата и длительность.
runtimeBuildId содержит MVID модуля исполняемого AgentCore: разные сборки
различимы и при одинаковом runtimeVersion, без чтения git на машине игрока.
Записываются старт/переподключение/остановка, наблюдение перед решением, начало и
конец модели, подготовка речи, commit/cancel/failure и исходы физических команд.
Наблюдения ограничены временем, положением и числовой сводкой инвентаря/видимости;
сырой prompt, ответ провайдера, исключение Message, ключи и голос не копируются.
Три одинаковых подряд отказа разных команд дают диагностический сигнал
`signal.repeated_failure`; повторный poll того же исхода не увеличивает счётчик.
Сигнал не является подтверждённым багом. Успешное действие сбрасывает серию отказов.
CLI `Tools/agent_diagnostics.py` также отмечает три одинаковых отказа шагов
одной цели и восемь модельных ответов без отправки команды. Это диагностические
гипотезы: разговоры и справочные запросы могут быть обоснованны. Итог шага
содержит сохранённую причину серверной квитанции даже без явного override.
Штатный abort передаёт `PlanInterrupted.<InterruptionCause>` через квитанцию
в сохраняемую очередь. После подтверждённого failed активная цель удерживает
контроль на время перепланирования; встроенный AI не подменяет её между решениями.
Явная пауза цели, отмена или остановка мира освобождают контроль по-прежнему.
Примеры причин: Crying, ThreatReroute или PathFailure. Свободный
внутренний текст причины в этот код не копируется; политика допуска прерываний
§121 не меняется. Модель различает источник отказа до следующего решения.
Нехватка инструмента при Harvest и data-driven gate даёт точный `MissingTool`.
MCP учитывает как RequiredCapabilities каталога, так и сохранённые legacy-гейты
исполнителя: Mine для валуна, Cut для юкки, ChopWood для дерева; лечебный куст
остаётся ручным сбором. `requiresAllCapabilityGroups` означает AND между группами
и ANY внутри группы; `requiresAnyCapability` — сокращение для единственной группы.
Переносимые вещи показывают `groundInteractions` из того же каталога: обработка
сырья не исчезает из справки после подбора. Эти операции требуют объекта в мире:
сначала Drop, новое наблюдение objectId, затем interact. Индекс инвентаря не objectId.

Ротация по 8 MiB, максимум 8 файлов и 30 дней. Файлы только для пользователя ОС.
Ошибка записи не останавливает действие: `diagnosticsError=DiagnosticsUnavailable`
публикуется в существующем status JSON, восстановление записи очищает ошибку.
Studio показывает локализованное предупреждение в строке состояния агента,
сохраняя действующий режим работы; доступность журнала не является остановкой.
Журналы не загружаются в серверный трекер автоматически.

Сборки macOS Studio публикуются рядом с игровыми билдами: по умолчанию
`~/hex-girls/AgentStudioReleases/v<version>/Agent Studio.app`, а ярлык
`~/hex-girls/Agent Studio.app` указывает на последнюю успешно проверенную версию.
Нумерация Studio независима от игры и увеличивается автоматически. Старые версии
и отчёты сохраняются; ярлык переключается атомарно только после проверки подписи.
Штатный упаковщик — `Tools/package_agent_studio.py`; он не компилирует и не запускает агента.

Эталон: утверждённый тёмный макет с бирюзовым акцентом. Также светлая тема,
RU/EN, Retina, Windows 125–200%, адаптивные поля, системные кнопки окон.
Визуальный эталон сохранён в `Docs/AgentStudioDesign/approved-mockup.png`.
Уточнение пользователя 2026-09-08: основной экран — небольшой пульт 560×300
с прокруткой, выбором агента, статусом, подключением/запуском/остановкой,
настройками и «AI · Сознание». Агенты и «+» находятся слева, управление — три
крупные иконки с подсказками, без текстовых подписей. Большие настройки, выбор сервера/NPC, архив
активности и документы открываются отдельно. Исходный макет остаётся эталоном
палитры и больших редакторов, но не размера главной панели.
Высота главного окна подстраивается под содержимое (прокрутка ограничивает рост);
«+» располагается под списком агентов, не растягивает пустой нижний ряд.
Статус центрирован, настройки обозначены крупной векторной шестерёнкой.
Окна интеграций и памяти используют навигацию слева и содержимое справа.
Окно серверов показывает сохранённый список и явные кнопки «Добавить сервер»,
«Изменить». Форма содержит адрес и скрытое поле токена, без кодов, галочки
администратора или отдельного запроса прав. Подключение проверяется перед
сохранением, без attachment или модели. При смене endpoint старый credential
не переносится автоматически на новый адрес.
Connect при отсутствии credential открывает настройку доступа выбранного сервера,
а не показывает безадресную сетевую ошибку; после авторизации загружает NPC.
Персонажи выбираются из списка, возвращённого сервером; несколько профилей
могут выбрать разные NPC одного игрока.
Сохранение выбранного NPC не очищает список; повторное открытие окна сохраняет
выбор. Подтверждение показывает имя и NPC ID, отдельно указывает, что AI не
запущен. Пустой список после успешного подключения отображается как отсутствие
доступных персонажей, а не как просьба снова подключить сервер.
Нажатие Connect сразу меняет подпись на «Подключаюсь…», показывает индикатор
ожидания и блокирует повторный запрос. Результат явно сообщает «Подключено»,
число доступных NPC и паузу мира, либо отказ/таймаут/ошибку. Сетевое ожидание
ограничено 35 секундами; закрытие окна отменяет ожидающее подключение.
Ожидание разрешения ОС на чтение токена отображается отдельно, не считается
сетевым таймаутом. При Connect сохранённый токен читается один раз, без второго
запроса в Keychain; отменённое ожидание не продолжает подключение позднее.
Каталог моделей и голосов загружается при открытии настроек, моделей — также
при смене провайдера. Нет автоматической замены выбранной модели, провайдера
или способа оплаты. Ошибка/отсутствие ключа видимы; неизвестные режимы мышления
не выдумываются. Codex возвращает режимы через официальный model/list.
Подтверждение выхода компактно объясняет остановку агентов и сохранение памяти;
кнопки внизу, отмена в начальном фокусе, Escape не завершает приложение.
Окна: управление, интеграции, серверы, память/душа. Голос и чат остаются в игре.
В Studio показываются краткие намерения/результаты, не chain-of-thought.
Вкладки памяти и души читают Markdown выбранного профиля без запуска модели:
MEMORY.md открывается по умолчанию, SOUL.md — непосредственно во вкладке души.
Список документов включает дневники, прошлые миры и Markdown импорта, но не
служебные/скрытые файлы и символические ссылки. Редактор открывает выбранный
документ и сохраняет его с проверкой версии. Activity отделяет текущий статус
от локальной истории (последние 32 сохранённых намерения/записи дневника с датами);
старый архив не считается действующим подключением. Connect имеет значок
соединения, запуск — Play, остановка — красный квадрат, рядом остаются подписи.
Проверяются изоляция профилей, остановка/пауза/повторы/права, пять модельных
интеграций (DeepSeek с мышлением и без), TTS fallback, отрицательная симпатия,
экспорт/импорт/конфликты и масштабирование на обеих ОС.

### §163.3d Срочная переноска и живые события (bug #413)

Известная цепочка поднятия, движения и укладывания исполняется единой очередью
без вызова модели между квитанциями. Навык `rescue-person` объясняет штатные
варианты `carry_person → put_person_in_bed` и `carry_person → GoHome → put_down_person`.
Нельзя выдумывать ещё не выбранный пункт назначения. Архивная синхронизация
`read_events` только сохраняет историю; не подаёт старые ранения повторно как
экстренное прерывание. Прерывания поступают из текущей ленты с курсором от
`attach_agent`. Свежая угроза, телесный отказ и отмена игрока сохраняют приоритет.
