## §174 HTML-интерфейс веб-клиента (iteration 174)

Веб-клиент (§168) стал основным. Его окна, собранные на UI Toolkit внутри
canvas, в браузере ведут себя хуже родной страницы: фокус ввода (#473),
масштаб, шрифты, доступность, а для Telegram Mini App нужен обычный HTML.
Решение игрока 17.10.2026: все окна веб-клиента переверстать на HTML.
Окна согласуются по одному, сборки до конца переделки не собираются, кроме
одной проверочной после первого окна (игровое меню).

### §174.1 Граница

- HTML-окна живут только в веб-плеере. Десктоп (macOS/Windows) остаётся
  клиентом для разработки и сохраняет окна UI Toolkit. Новых окон на десктоп
  не делаем: окно, переведённое на HTML, дальше развивается только в HTML.
- Логика окна остаётся в C#: когда открыть, что делает кнопка, пауза мира,
  сохранение. Страница получает модель (JSON) и возвращает команды. Окно
  не узнаёт ничего о симуляции в обход C#.
- В Unity остаётся то, что привязано к 3D: облачка речи и полоски над
  головами, кукла персонажа и превью в лобби. Для куклы и превью HTML-окно
  оставляет прозрачную область, а Unity рисует под ней. Отладочные панели
  (`UnityDebug`) пока остаются на UI Toolkit.
- Пока страница не ответила (редактор, десктоп, старая закэшированная
  страница), `HtmlUi.Active == false` и окно показывает свою UI Toolkit-версию.

### §174.2 Мост: C# пишет, страница кладёт в очередь

Тот же приём, что у сокета (§168.2): JS никогда не вызывает C#.

- `HtmlUi.cs` (C#) и `HexHtmlUi.jslib`: `HexUiPost(json)` передаёт сообщение
  странице; раз в кадр `HtmlUi.Pump` (порядок исполнения −10000) забирает
  очередь команд `HexUiTake()` (до 64 за кадр) и биты владения
  `HexUiPointer()`.
- `ui/bridge.js` — страничная половина: `receive`, `take`, `pointerBits`.
- Рукопожатие: C# на старте шлёт `hello {v}`, страница отвечает `ready {v}`.
  Только при совпадении `HtmlUi.Protocol` и `PROTOCOL` в `bridge.js`
  включается HTML-интерфейс; несовпадение — предупреждение в лог и UI Toolkit.
- Сообщения C# → страница: `strings {lang, terms}`, `show {screen, model}`
  (новое окно открывается поверх остальных; `show` уже открытого окна только
  меняет модель и порядок не трогает — HUD, обновляемый раз в секунду, не
  вылезает поверх диалога; поднять окно — `hide`, затем `show`),
  `hide {screen}`, `asset {key, url}` (протокол 2: картинка, на которую
  модели ссылаются по ключу; `HtmlUi.Asset` шлёт каждый ключ один раз, чтобы
  обновление модели не тащило картинки). Страница → C#: `ready {v}`,
  `cmd {screen, cmd, args}`.
- Окно в C#: `HtmlUi.Handle(screen, (cmd, args) => …)`, затем
  `HtmlUi.Show(screen, model)` / `HtmlUi.Hide(screen)`. Модель и аргументы —
  `JObject`, без сериализации по отражению (IL2CPP).

### §174.3 Ввод, фокус, полный экран

- Корень `#hex-ui` прозрачен для мыши (`pointer-events: none`); окна и
  подложки помечены классом `hx-surface`. Биты для Unity: 1 — курсор над
  `hx-surface`, 2 — нажатие началось на HTML и ещё держится, 4 — фокус в
  текстовом поле страницы.
- `HtmlUi.BlocksWorldInput` (биты 1 и 2 плюс кадр отпускания) входит в
  `RuntimeWindow.BlocksWorldInput`, а его уже читают все проверки ввода в мир
  (`SimulationInputAdapter`, `RtsCameraController`). Отдельные флаги окон не нужны.
- Unity по умолчанию забирает все клавиши документа
  (`WebGLInput.captureAllKeyboardInput`), и в HTML-поле нельзя было бы
  печатать. Пока установлен бит 4, `HtmlUi.Pump` выключает захват, а потом
  включает обратно. Клавиатурные сокращения игры (Escape и прочие) остаются
  в C#.
- Полноэкранный режим включается на `#hex-stage` (canvas вместе с `#hex-ui`),
  а не через `unityInstance.SetFullscreen`: тот растягивает один canvas, и
  HTML-окна оставались бы за кадром.

### §174.4 Строки — только I2 (§58)

У страницы нет своей таблицы строк. После `ready` и при каждой смене языка
C# отправляет всю таблицу текущего языка (`LocalizationManager.GetTermsList`
через `Loc.Get`, около 3.5 тыс. терминов). В JS строка берётся через
`t(key, vars)` из `ui/i18n.js`; контракт тот же, что у `Loc.Get`: пропавший
термин показывается своим ключом. Новая строка окна — новый термин в
`I2Languages.asset`, как и для десктопа.

### §174.5 Единый вид

- `ui/theme.css` — токены и общие классы: `hx-backdrop`, `hx-window`,
  `hx-btn` (`--primary`, `--danger`), `hx-disclosure`, `hx-slider`.
  Палитра взята из окон UI Toolkit (`GameMenu`, `RuntimeWindow`): тёмная
  панель, золотой основной цвет, красный только при наведении на опасное
  действие.
- `ui/components.js` — `ModalWindow`, `Button`, `Disclosure`, `Slider`.
  Окно собирается из них и не перекрашивает их.
- Размеры только в `rem`. `ui/main.js` ставит корневой шрифт по высоте
  игровой области: 16 px на 900 px, в пределах ×0.8…×1.5 (на нынешнем
  холсте 960×600 — 12.8 px). Общие сбросы стилей обёрнуты в `:where()`,
  чтобы не перебивать классы компонентов.

### §174.6 Страница и сборка

- Шаблон `Assets/WebGLTemplates/HexLive/`: `index.html` (canvas, `#hex-ui`,
  загрузка, полный экран), `TemplateData/style.css`, папка `ui/`.
  `HexLiveWebGLPlayerBuild.Build` выставляет шаблон `PROJECT:HexLive` только
  на время сборки и возвращает прежний (настройка общая с десктопом).
- После сборки `RequireHtmlInterface` проверяет `ui/main.js`, `ui/bridge.js`,
  `ui/theme.css` и подключение `ui/main.js` в `index.html`; без них сборка
  падает. Он же сверяет каждый файл `ui/` в результате с исходником побайтно:
  препроцессор шаблонов Unity не должен ничего в них поменять. Строка лога:
  `[WebGLBuild] HTML interface: ui/ from template HexLive, N files verbatim`.
- Шаблон сам ставит `config.devicePixelRatio = 1` с меткой §168.11;
  `CapDevicePixelRatio` проверяет строку и пишет прежнюю строку лога.
- Без сборщика: Preact 10.29.8 и htm 3.1.1 лежат в `ui/vendor/` как
  ES-модули (`.js`, не `.mjs`: не каждый сервер знает этот MIME), лицензии
  рядом. Unity прогоняет файлы шаблона через свой препроцессор, поэтому в
  коде `ui/` нельзя писать `{{{`, `<<<` и строки, начинающиеся с `#if`,
  `#else`, `#endif` (селекторы вида `#hex-ui {` безопасны: ими начинается и
  стандартный `style.css` Unity). Проверочная сборка (§174.7) это подтвердит.

  колонистки), модель шлётся при сдвиге доли на 0.5 % или новом статусе, а

  миров и выбор режима остаются UI Toolkit (§174.1). Строки статуса
  `ContentAssetService.Status` не локализованы (зашитый русский) и пока идут
  как `status.text` — долг §58. Ошибка подключения показывается на карточке,
  и строки снова нажимаются (UI Toolkit-панель оставляла их выключенными).
- `creator` — создание персонажа (§171.20). Поток (аккаунт, варианты,
  черновик, замороженная попытка, Web Lock, POST) и 3D-превью остаются в C#;
  страница рисует форму. Превью — прозрачное окно: вокруг себя оно закрашивает
  экран широкой тенью, а внутри Unity рисует камеру превью прямо в
  прямоугольник `previewRect` (`camera.rect`, без RenderTexture в UI Toolkit);
  арт титульного экрана на это время прячется. Поле имени — HTML-`input`:
  бит 4 моста отдаёт клавиатуру странице, и ловушка фокуса #473 исчезает
  целиком. Миниатюры скинов и причёсок по-прежнему рендерит
  `LobbyAppearanceThumbnails` и отдаёт странице картинками (`thumbs`); цвета
  волос и глаз — плоские образцы из `HairTintPalette` и `PeopleEyeColour`.
  Характеристики и навыки показаны целыми очками 0–10 при бюджете 42 и 30
  (серверные 0–1 и 4.2/3.0 ×10) и задаются той же шкалой из десяти ячеек
  `Pips`, что в окне «Ваш персонаж» (просьба игрока 18.10.2026: один элемент
  и там, и тут). С `onChange` она управляемая: клик по ячейке ставит значение
  (повторный клик по последней закрашенной снимает одно деление), «−» и «+»
  по краям, стрелки клавиатуры; ячейки сверх оставшегося бюджета приглушены и
  не нажимаются — перебрать очки нельзя. Лагерь показывает «Живут: N из M»
  и полоску заполненности (§171.10, решение 18.10.2026); старый сервер без
  этих полей — без строки. Противоположные черты (Неряха/Чистюля,
  Лентяйка/Трудяга, Трусиха/Храбрая) стоят парой и исключают друг друга.
  Шаги «Внешность → Способности → Лагерь»; имя видно на всех шагах; причина,
  по которой нельзя идти дальше, пишется рядом с кнопкой. Раскладка
  складывается в колонку по ширине ИГРОВОЙ области (container query), а не
  окна браузера.
- Подключение `creator`: `PlayerCharacterCreationFlow` и `PlayerCharacterCreator`

### §174.8 Стенд

`python3 Tools/webui_stand.py` → http://localhost:8091/. Стенд грузит те же
файлы `ui/`, а вместо Unity отвечает `Tools/webui/stand.js` тем же
протоколом и с тестовыми данными; журнал справа показывает команды, которые
получил бы Unity. Строки стенд берёт прямо из `I2Languages.asset`
(`--export-i18n <dir>` пишет их в JSON); в игре их присылает C#. На стенде
окно согласуется с игроком до того, как его подключат в C#.

### §174.9 Страница до старта Unity: загрузчик и окно игры

Решение Толи 18.10.2026: игра начинается «сразу во весь экран», до неё —
сайт (§171.12), загрузка в стиле сайта и без логотипа Unity. Владельцы
согласованы: шаблон страницы (`index.html`, `TemplateData/`) — сессия сайта,
`ui/**` — сессия HTML-интерфейса, splash Unity и сборка — владелец WebGL.

- **Без входа — на сайт.** Если в `localStorage["hexlive.session"]` нет живой
  сессии и host отвечает на `/api/accounts/v1/client-config` (аккаунты на нём
  есть), страница сразу уходит на `/login/` и не качает плеер. На host без
  аккаунтов (локальный `webgl_serve.py`) ничего не меняется; `?guest`
  оставляет анонимный просмотр (зрители, проверки без аккаунта).
- **Загрузчик** (`#unity-loading-bar`) — титульный арт и логотип игры
  (`TemplateData/loader-bg.webp`, `logo.webp`), логотип там же, где его ставит
  `LoadingScreen` (36, 20, 360 при высоте 1080), поэтому переход в титульный
  экран Unity бесшовный. Снизу — полоса загрузки в виде `hx-loading`:
  «Загружаем игру» по доле скачивания (Unity даёт 0–0.9, показываем как
  0–100%), затем «Готовим остров». Строки — RU/EN по `hexlive.language`;
  это несколько слов страницы до Unity, I2 им недоступен. После старта
  загрузчик гаснет за 450 мс. Надписи и логотип Unity в шаблоне нет; splash
  «Made with Unity» выключает `HexLiveWebGLPlayerBuild`
  (`PlayerSettings.SplashScreen.show = false` на время сборки).
- **Окно игры = окно браузера.** `#unity-container` — `position: fixed;
  inset: 0`, холст и `#hex-ui` растянуты на всю сцену и всегда одного размера
  (ему считает rem и прямоугольник превью редактора, §174.5). Прежний
  фиксированный холст 1920×1080 по центру и подвал под ним убраны; кнопка
  полного экрана — маленькая в правом верхнем углу (единственный свободный
  от HUD: погода слева, скорость по центру, список колонисток с 4.25rem, карточка
  персонажа по низу), в полном экране скрыта.
- **Буфер не больше 1080p** (условие владельца WebGL): строка
  `config.devicePixelRatio = 1;` остаётся дословно (её ищет сборка, §168.11),
  сразу за ней `devicePixelRatio = min(1, √(1920·1080 / площадь сцены))`,
  пересчёт на resize и смене полного экрана. Unity копирует `config` в свой
  `Module`, поэтому после старта значение пишется в `unityInstance.Module`.
  `?dpr=` (0.25–2) умножает его для замеров (`?rscale=` занят URP renderScale). Проверено: окно 2560×1440 →
  CSS-холст 2560, буфер 1920×1080.
- **Полный экран с первого клика.** Браузер даёт fullscreen только внутри
  жеста, а переход с сайта на страницу игры жест не переносит. Поэтому первый
  клик на странице (обычно «Играть» в карточке серверов) после обработки
  разворачивает `#hex-stage` (§174.3). Именно `click`, а не нажатие: сцена
  растёт и сдвинула бы кнопку из-под указателя. Один раз за страницу — выход
  по Esc остаётся за игроком.
