## 24. Planning System (Deep)

This section defines how a selected goal is transformed into a concrete, executable sequence of steps.

**Core idea:**

Decision chooses WHAT to do. Planning determines HOW to do it.

### 24.1 Planning Pipeline

```
Selected Goal → Target Selection → Plan Construction → Reservation → Validation → Plan Ready
```

### 24.2 Plan Structure

```csharp
class NPCPlanState
{
    public GoalType Goal;

    public List<PlanStep> Steps;
    public int CurrentStepIndex;

    public PlanStatus Status;
}

class PlanStep
{
    public PlanStepType Type;

    public TileCoord? TargetTile;
    public JunctionId? TargetJunction;
    public ObjectId? TargetObject;

    public int? TimeoutEndTick;
}
```

```csharp
enum PlanStepType
{
    MoveToTile,
    MoveToJunction,
    Interact,
    Wait,
}

enum PlanStatus
{
    None,
    Active,
    Completed,
    Failed,
    Invalid
}
```

### 24.3 Target Selection

Planner must select a concrete target.

**Example for Eat:**

- scan perceived objects
- filter reachable
- sort by distance / availability
- pick best candidate
- ObjectId SelectFoodTarget(NPCState npc)

**v1 candidate filter (iteration 3):** a perceived object qualifies only if it
is reachable, offers the goal's interaction, and is not occupied by another
NPC (occupied-by-self counts as available — an NPC mid-interaction must not
lose its own target). This is the RequiresObjectFree condition from 29.6
applied at selection time; junction reservation remains the race arbiter.

### 24.5 Reservation Integration

Before committing to a plan, required points must be reserved.

```csharp
bool TryReserve(JunctionId point, EntityId npc)
If reservation fails:
try another target
```

or fail planning

### 24.6 Plan Validation

Plan must be validated before execution.

**Checks:**

- path exists
- target still valid
- reservation successful
- If invalid → planner retries or returns failure.

### 24.7 Plan Execution Flow

```
Plan Active → Execute Step 0 → Step Completed → Execute Step 1 → ... → Plan Completed
```

### 24.8 Step Completion Rules

Each step must define completion condition.

**Examples:**

- MoveToTile → reached tile
- MoveToJunction → reached point
- Interact → execution finished

### 24.9 Plan Failure

**Plan may fail due to:**

- target lost
- path invalid
- reservation lost
- timeout

**On failure:**

- mark plan invalid
- trigger replan

### 24.10 Replanning Strategy

Replan should not happen every tick.

**Triggers:**

- plan invalid
- goal changed
- target unavailable

**Policy:**

- delay replanning by cooldown
- avoid loops

Revision 2: `Goal=None` has nothing to plan, and an already completed
`Goal=Idle` plan is stable until the auction selects another goal. Neither is
rebuilt on every Medium tick merely to reproduce the same empty plan.

### 24.11 Timeouts

Each step may have timeout.

```csharp
if (currentTick > TimeoutEndTick)
```

    step fails

### 24.12 Minimal v1 Planner

**Keep planner simple:**

- no GOAP initially
- direct mapping goal → steps
- basic target selection
- basic validation

### 24.13 Debug Requirements

**Planner debug must show:**

- current goal
- selected target
- steps
- current step index
- failure reason

### 24.14 Design Rules

- Plan is a sequence of explicit steps
- Each step must be independently validatable
- Planner must not assume success
- Reservation must happen before execution
- Replanning must be controlled, not constant

### 24.15 Summary

**Planning System answers:**

Given a goal, how exactly will the NPC achieve it step by step?
It transforms intention into an executable structure.

### 24.16 Bounded occupied-path recovery (14 Aug 2026)

An occupied next junction is a wait with a budget, not a new path every tick.
For a manual route or a plan following a live agent, the counter survives
repathing: at 41 blocked ticks movement requests one alternate route; at 81 it
shuns the concrete target when one exists, applies the normal goal cooldown,
emits `PathOccupied` and aborts the plan. Any real positional progress clears
the counter.

Revision 2: the first 41-tick window is also the complete budget when the
occupied node is the **final** work point of an in-place craft. There is no
graph detour around a destination. The plan is released without a goal
cooldown, its congestion attempt is forgotten by the loop ledger, and the
auction runs again. Ground-pile selection excludes a pile whose exact anchor
junction is occupied by another actor, so the new plan chooses another cluster
or waits without claiming that the craft is presently available.

The same one-window rule applies to the final point of every autonomous plan
without `TargetAgent`: another actor standing on a log, carcass, work object or
location such as a cooling spot cannot make the owner rebuild the identical
terminal route twice. An object is not shunned and the goal is not cooled down,
because congestion says nothing about the target itself.
Manual movement keeps the ordinary two-window recovery budget, while
agent-targeted actions remain governed by their dedicated aid/combat rules.

Revision 3: an autonomous route with no `TargetAgentId` uses a shorter 17-tick
courtesy window and a 33-tick total budget (one repath). This is deliberately
below the 64-tick stillness detector: an already-known occupied step must be
resolved before it can be reported as an unexplained stall. Manual movement and
live-agent following keep 41/81 because they preserve explicit/reactive intent.
The bid and generic object planner both include this exact direct anchor (or
the object's interaction rim) in availability: while it is occupied or claimed
by another NPC they select a different target, or withhold the goal, instead of
immediately rebuilding the released route.
Exact availability uses actors' live `CurrentJunction`/claimed nodes as the
authority in addition to the coarse occupancy table; a stale occupancy entry
must not let decision and movement disagree about whether the endpoint is free.

Decision and planning share exact target selectors. In particular a ledge seat
must have valid edge geometry, be reachable and free, and not belong to a build
site; a garment must pass the same fit/ownership/benefit mode that its Dress
plan will use.

The shared object selector also proves that at least one exact interaction-rim
junction is free, reservable and reachable with the NPC's present jump ability.
Perception's broader “a route exists beside it” fact is insufficient: a tool
boxed in by furniture or actors must not win the auction and then fail every
four ticks. The rim scratch storage is owned by `WorldState`, never static.
