## 32. NPC Brain & AI Architecture Layer (GOAP / LLM / Hybrid)

This section defines the meta-layer that organizes decision-making strategies and allows swapping or combining different AI approaches.

**Core idea:**

The Brain is not a system. The Brain is a composition layer that selects HOW thinking happens.

### 32.1 Brain Position in Architecture

```
Perception → Brain → Decision Model / Planning Model → Execution
```

The Brain orchestrates how decisions and plans are produced.

### 32.2 Brain Structure

```csharp
class NPCBrain
{
    public IDecisionModel Decision;
    public IPlanningModel Planner;
}
```

This allows different AI strategies to be plugged in without rewriting systems.

### 32.3 Decision Model Interface

```csharp
interface IDecisionModel
{
    DecisionResult Decide(NPCContext context);
}
```

**Implementations:**

- UtilityDecisionModel (current v1)
- RuleBasedDecisionModel
- LLMDecisionModel (future)

### 32.4 Planning Model Interface

```csharp
interface IPlanningModel
{
    NPCPlanState BuildPlan(NPCContext context, GoalType goal);
}
```

**Implementations:**

- SimplePlanner (current v1)
- GOAPPlanner
- ScriptedPlanner

### 32.5 Current v1 Brain (Simple)

Decision: Utility AI
Planning: Direct mapping (Goal → Steps)
This is stable, debuggable, and fast.

### 32.6 GOAP Integration (v2)

GOAP replaces simple planner.

```
Goal → World State → Actions (preconditions/effects) → Search (A*) → Plan
```

GOAP is powerful but more complex.

**Recommendation:**

- do not start with GOAP
- introduce after v1 is stable

### 32.7 LLM Integration (v3+)

LLM should not control simulation directly.

**Correct role:**

- high-level reasoning
- narrative behavior
- suggestion of goals or priorities

```csharp
class LLMDecisionModel : IDecisionModel
{
    public DecisionResult Decide(NPCContext context)
    {
        // interpret context → propose goal
    }
}
```

**Important rule:**

- LLM outputs must be validated and converted into structured goals.
- Never allow free-form LLM output to mutate world state.

### 32.8 Hybrid Brain Model

Recommended long-term architecture:
Utility AI (fast, reactive)

+ GOAP (structured planning)
+ LLM (high-level reasoning)

**Each layer has its role:**

- Utility → fast selection
- GOAP → structured execution
- LLM → creativity / variation

### 32.9 Brain Modes

NPCs may have different brain types.

**Examples:**

- Simple NPC → Utility only
- Advanced NPC → Utility + GOAP
- Special NPC → Utility + LLM hybrid

```csharp
enum BrainType
{
    Simple,
    Advanced,
    Narrative
}
```

### 32.10 Stability & Safety

**Brain layer must enforce safety rules:**

- no infinite loops
- no invalid goals
- no unsafe commands
- LLM-specific rules:
- validate outputs
- fallback to utility if invalid

### 32.11 Debug Requirements

**Brain debug must show:**

- active decision model
- active planning model
- raw decision result
- fallback usage
- LLM outputs (if used)

### 32.12 Minimal v1 Scope

**For first implementation:**

- NPCBrain abstraction exists
- UtilityDecisionModel
- SimplePlanner

No GOAP, no LLM yet.

### 32.13 Design Rules

- Brain orchestrates, not replaces systems
- Decision and Planning must be swappable
- LLM must be sandboxed and validated
- Keep v1 simple and deterministic
- Add complexity only after stability

### 32.14 Summary

**NPC Brain answers:**

How does this NPC think, and which decision/planning strategy does it use?
It is the abstraction layer that future-proofs the AI architecture.

### 32.15 LLM-control MVP adapter (Slices 1-5)

The MVP is an opt-in control adapter, not a replacement Brain. A provider sees
only an immutable, deterministic `LlmDecisionContext`; its structured decision
is validated by `LlmCommandTranslator`, then Slice 3 dispatches the resulting
command through `ManualCommandExecutor.Apply`. It never mutates NPC state
directly and never bypasses the ordinary pathfinding, movement, interaction or
combat systems.

The shipped registration is safe by default in two independent ways:

- `SpecLlmControl.Enabled` defaults to `false`;
- the default `LlmControlSystem` has no selected NPC ids.

The simulation assembly contains no network or API provider. Only the explicit
enabled/test constructor may create the deterministic offline
`MockLlmControlProvider` when a provider was not supplied.

An explicitly enabled system runs on the Medium layer after rescue assignment
and before `DecisionSystem`. It consults only selected, living colony NPCs that
are genuinely idle: no goal, active plan, active/waiting execution, movement,
combat, carry link or manual attack order. Every consultation starts a 64-tick
cooldown, including `None`, invalid and provider-failed outcomes, so failures
cannot become per-tick spam. A non-`SetManualControl` decision first sends
`SetManualControlCommand(true)` through the same executor and proceeds only if
manual mode was accepted. Adapter acceptance, translation/manual rejection and
provider exceptions are diagnostic trace events; command semantics and their
own rejection reasons remain owned by the manual-command executor.

Slice 4a makes the provider boundary asynchronous without making the simulation
itself async. `ILlmControlProvider` is a request/drain contract:

- `TryRequest` only enqueues immutable `LlmControlRequest` work and must return
  without waiting for provider reasoning;
- the provider owns its worker lifetime and a thread-safe result queue;
- `TryDequeueResult` is the only way completed, failed or canceled work returns
  to the simulation thread;
- every result repeats request id, NPC id and the context's issued tick. No
  provider worker receives `WorldState` or applies a command.

`LlmControlSystem.Run` is a two-phase pump. It first drains only results from
earlier pumps, then fills free request slots. Thus even an immediately completed
mock result cannot be issued and applied in one system pass. Before applying a
completed result, the system requires the exact matching in-flight request,
drops it once its issued tick is 64 or more ticks old, and re-runs the full
admission gate against the current world (selected living colony NPC, conscious,
idle, not fighting/carrying/moving and with no active goal, plan, execution or
manual attack). Translation and `ManualCommandExecutor` then perform their
ordinary payload and current-world validation.

Scheduling is bounded and fair: at most two provider requests may be in flight
globally, never more than one per NPC. The opted-in roster is de-duplicated and
sorted by entity id, but selection starts at a rotating cursor, so a full cap
cannot permanently favor the lowest ids. The 64-tick cooldown starts when a
request is issued, including rejected or failed submissions.

An unanswered request times out after 64 ticks, releases its slot and cancels
its token. A result arriving after timeout or with a mismatched identity/issued
tick is diagnostic-only and never mutates the world. Disposing the system
cancels every in-flight token, disposes the owned provider and makes later pumps
inert; provider teardown is cooperative and must not wait for external latency.

Slice 4b supplies the first real provider only in the headless server host. The
simulation assembly remains network-free. The host provider posts deterministic
context to an explicitly configured HexLive gateway; it does not assume or ship
an external-model endpoint. The server stays disabled by default and requires
both an endpoint and a non-empty selected-NPC list before constructing the
provider.

Slice 5 locks that gateway boundary as JSON contract version 1. Requests and
responses use exact camel-case property names and exact enum names; every request
carries `contractVersion`, and every response must carry the same supported
version plus `commandKind`. Unknown fields, incompatible versions, malformed or
oversized/non-JSON responses fail closed and enter provider backoff. Command
payloads still pass through `LlmCommandTranslator` and the ordinary manual
executor before they can affect the world. The complete JSON/header/payload
contract is `Server/HexLive.Server/Llm/CONTRACT.md`.

Operational configuration is accepted through validated `HEXLIVE_LLM_*`
environment variables and equivalent non-secret command-line options. The bearer
key is environment-only so it is not exposed in process arguments. Non-loopback
endpoints require HTTPS, partial opt-in fails startup rather than silently doing
nothing, and request timeout/backoff/queue/concurrency values have finite bounds.
Only an endpoint and/or NPC roster expresses opt-in. A stray API key, model hint,
or tuning variable is ignored until that opt-in exists, so unrelated environment
state cannot break an ordinary server startup or `--help`.
