## §41 Loading, Save & Offline Progression (iteration 37)

### 41.1 Loading screen (pause-until-ready)
Play mode used to drop straight into a live world (`startPaused: false`),
so the sim ticked while Unity was still spawning terrain/actors — then the
runner's accumulator "caught up" with a burst of ticks (visible stutter +
time jump). New flow: the runner starts PAUSED; a full-screen loading
overlay (UIDocument, top sorting order) drives phases:
1. **World** — bootstrap the WorldState (synchronous, cheap).
2. **Time passed** — if a save exists, restore the model blob (§41.2 v2),
   then wind forward by `offlineTicks` (§41.3) on a WORKER THREAD while the
   main thread pulls content; the curtain drops when both are done.
3. **Island** — let `HexWorldRenderer` build all views (terrain mesh,
   actors, wardrobe) behind the overlay for a few frames. Addressables prewarm
   is scoped to content the FINAL world needs — worn and dropped garments,
   hairstyles, prostheses (`ScenePrewarm`, §41.3) — never the entire wardrobe
   catalog; future content remains lazy. Icons and item models are the
   exception and are warmed whole, being one small bundle and one folder.
4. **Warm-up** — select each NPC once (builds the character panel UI,
   portrait camera + its RenderTexture, shader variants) so the FIRST real
   click has no hitch — this was the "заход в персонажа" lag: the whole
   panel tree + portrait pipeline built lazily on first selection.
5. The curtain stays opaque until each opening actor has more than a body
   GameObject: all Addressables work is complete, every current `WornItem` has
   passed the wardrobe synchronisation attempt (including the established
   art-less/slot-conflict terminal cases), the selected hairstyle/colour is
   applied, and the first roster NPC is selected. Because the world is still
   paused, the RTS camera is placed on that NPC immediately (not through
   scaled-time `SmoothDamp`). The loading boundary also guarantees
   `Time.timeScale = 1`: the simulation clock is unscaled and otherwise a stale
   Escape-menu pause can move roots while freezing every Animator, which
   appears as foot sliding. Only then fade out, unpause, and start the autosave
   timer.
The hair and hair-colour Addressables caches are session caches, not process
caches. They are cleared at `SubsystemRegistration` (Enter Play Mode may run
without a domain reload), and every cached or completed handle is checked with
`IsValid()` before `IsDone`, `Status`, or `Result` is read. A handle invalidated
by Addressables teardown is discarded and resolves the actor's pending hair
attempt as a terminal miss; it may never throw out of the coroutine and leave
the loading curtain waiting forever.
The macOS Player keeps URP's GPU Resident Drawer and its camera occlusion off.
Hex tiles, terrain and most world props are generated at runtime; Unity 6's BRG
occlusion path can classify that whole dynamic layer as invisible while skinned
actors and incompatible tree renderers remain visible. The release entry point
must reject a PC pipeline asset with either switch enabled rather than publish
an actors-only island.
Every desktop Player process requests a `1920×1080` render surface in
`FullScreenMode.ExclusiveFullScreen` before the first scene renders. The matching
PlayerSettings defaults are also Full HD, but startup reapplies the contract so
resolution preferences persisted by an older build cannot reopen the game in a
small window. macOS Retina support is disabled in PlayerSettings: the Player
must allocate one Full HD pixel surface rather than a doubled backing surface.
Full HD is authored in POINTS: on a display whose own modes are
16:10 the frame is letterboxed — black bars above and below — and that is the
intended look. `FullScreenWindow` must not be the default, because it adopts the
desktop's own surface instead of the requested one: on a Retina panel in a
scaled mode that silently renders 2880×1800 (5.2 Mpix) where 1920×1080
(2.1 Mpix) was authored, at ~2.5× the pixel cost. Two escape hatches relaunch
into the other behaviours without a rebuild: `-hexlive-borderless` restores the
borderless surface, `-hexlive-native-resolution` asks for the panel's own size.
Startup logs what it GOT, not only what it asked for — `[Display] APPLIED …`
carries the real `Screen`, mode, dpi and rendering size, and a declined request
is called out as `[Display] NOT Full HD`. Request-only logging is what let this
regression read, for several releases, exactly like a working contract.
External Addressables content has one distribution-level home:
`<build folder>/HexLiveContent/<BuildTarget>`. Windows/Linux reach it one level
above `<name>_Data`; macOS reaches it two levels above `<name>.app/Contents`.
Building the Player never rebuilds Addressables: the project setting is the
explicit `DoNotBuildWithPlayer` enum value (not `PreferencesValue`, whose
global Editor preference defaults to building). Content is rebuilt only via
`HexLive ▸ Addressables ▸ Собрать контент` when its source assets change.
Для точечного ремонта уже установленной macOS-папки команда
`HexLive ▸ Addressables ▸ Собрать и установить только недостающие иконки`
собирает только группу `HexLive.Icons`, добавляет её локации в существующий
catalog без замены хэшей wear/hair и устанавливает один icon bundle вместе с
обновлёнными `catalog.bin/.hash`. Полную пачку гардероба эта команда не строит
и не копирует.
The macOS runtime rewrites legacy catalog internal ids that pointed inside the
`.app`, so existing bundle/catalog output remains reusable without rebuilding
or copying it into every new application package.
Background art: `Resources/HexLive/UI/loading_island` (fal.ai-generated,
the three girls at sunset on the low-poly island, 1920×1080). Game logo
`Resources/HexLive/UI/logo` ("HEX ISLAND SURVIVE", alpha-cut) overlays the
art top-left; no text titles are drawn by code.
Anti-burst guard (independent of loading): the tick accumulator is clamped
to `TickDeltaTime × 12` (≈3 game-seconds of backlog) — a frame hitch may
never turn into a catch-up burst; at 50× the per-frame budget (~0.8 s) is
far below the clamp, so top speed is unaffected.

### 41.2 Save format — the save IS the model (v2, iteration 39)
v1 stored `{seed, tick}` and REPLAYED the deterministic history on load.
That dies the moment non-deterministic inputs arrive — player commands and
LLM decisions (§40.16) can't be replayed from a seed — and replay time grew
with total played ticks. v2 serializes the model in full:
`WorldSaveSerializer` (Simulation/Persistence, pure C#, versioned binary)
writes every piece of state the sim can mutate — tick, environment/weather,
build project, runtime tile flags (HasFloor/Indoor) and junction
Blocked/Door sets, all world objects, all NPCs (needs, mind, plan,
execution, movement, perception, memory, social, inventory, worn items,
body/wounds — incl. the §50 `Severed` set, §44 bandage/gauze zones, body
wetness and the §53 compassion trait, blob v14; before v14 those five were
dropped on load, so a reloaded amputee regrew the limb and stood back up.
Blob v15 closes the rest of that class: the §49 sickness window +
damage budget (`SickUntilTick`/`SicknessDamageRemaining` — a reload used to
cure the 🤢), the §53 `Compassion` need, the §35.4 overheat latch +
cool-off re-arm counter, and the §40.6 redress list (which exact shore
garments to put back on and where — a mid-bathe save no longer strands
her naked). Still transient BY DESIGN: combat pacing timestamps
(strike/flee/standoff windows) restart on load, and
`DreamQueue`/`ActiveDream`/`CurrentDream` are derived — `DreamSystem`
recomputes them from the saved `CampfireDreamDone` latch + bed ownership),
wildlife (dogs/rabbits/sharks), reservations, occupancy and
the runtime caches (verbatim, list order preserved — systems iterate
them), plus the wildlife respawn timers (moved into `WorldState` from
system-local fields, which silently reset on load).
Blob v16 added the §71 `Breath`; v17 the §72 `Faction`; **v18 the §74
appearance** — `SkinSet` / `Hairstyle` / `VoiceBank` per NPC, alongside the
`DisplayName`/`ActorMesh` that have been written since v3. All three are
empty in a pre-v18 save, and empty means "the mesh's own", so an old colony
loads back as the four shipped girls, unchanged. Static topology —
tiles, junction ids, adjacency, content catalog — is REBUILT from the seed
by `WorldStateFactory`, never stored; the blob is tens of KB.
Each local world lives in its own directory:
`Application.persistentDataPath/saves/<world-id>/world.dat` — a small header
`{magic, version, seed, tick, unixSeconds, speed, mode}` (read alone for the
menu, §41.4/§41.8) followed by the blob. The file is written to `.tmp` and
swapped whole so a crash mid-write can't eat the old save. Autosave every 60
real seconds + on quit / play-mode exit updates ONLY the selected world.
A corrupt/mismatched slot is preserved on disk for recovery and falls back to
a newly allocated world; it is never silently deleted. The pre-catalog
`Application.persistentDataPath/hexlive_save.dat` is moved once into a
`legacy-<seed>` world directory after its header is validated, so upgrading
does not lose the existing colony.
NOT serialized, by design: trace events (no sim effect), decision debug
scores (rewritten every pass), the junction-components cache (derived,
rebuilt on first pathfind). Dictionary ITERATION order is inherently
unsaveable (bucket/freelist internals): a restored world is content-
identical — headless-proven byte-exact on re-serialize across 4 seeds —
and simulates identically for a window (measured 0–1600 ticks), after
which enumeration-order differences make it a sibling world, not a wrong
one. Accepted: the design premise of v2 is that determinism is going away
anyway.

### 41.3 Offline progression
On load, elapsed real time becomes game time: `offlineTicks =
(now − save.unixSeconds) × 4` (1 tick = 0.25 s at 1×), **uncapped** — the
colony lives exactly as long as the game was closed. (Until iteration 2026-08
this was clamped to 7200 ticks = 3 event cycles = 30 real minutes, which made
an hour away and a week away identical: 0.3 of a visual day. The clamp is gone
by player decision; the only remaining numeric limit is arithmetic — `save.tick
+ offlineTicks` must stay a positive `int`, so `OfflineTicks` subtracts the
already-lived tick from its headroom.)

The stop condition is therefore a STATE, not a number: the wind loop halts the
moment **the colony is extinct** — no living NPC allied to `Faction.Colony`
remains (`LoadingScreen.IsColonyExtinct`). Note this cannot ride on
`World.Completed`, which means the raft launched (§40.15, currently disabled),
and it cannot count `Entities.Npcs` bare: a dead girl does not vanish, she
moves to `Entities.Corpses` (§28.15C v3), and a surviving hostile outsider
(§72) must not keep an empty world winding.

**The wind runs on a WORKER THREAD** (iteration 2026-08), not in per-frame
chunks on the main one. It used to hold a frame budget — 10 ms, then 120 ms —
and both were the wrong trade: the main thread was simultaneously the only one
allowed to read the disk, so winding and loading art took turns instead of
overlapping. Now the worker steps the world at full CPU speed while the main
thread pulls content; the budget constant is gone.

The world belongs to the worker EXCLUSIVELY for that window, which is what
makes it safe: the simulation assembly does not reference `UnityEngine` at all
(the same sources compile headless under .NET 9) and the pathfinder's scratch
buffers are already `[ThreadStatic]`; `CreateSnapshot` returns null while
`IsReplaying`, which gates every per-frame consumer at once rather than per
panel; the renderer and `SoundManager` leave `Update` on their first line;
`LocalEngineBackend.Tick` does nothing while the clock is paused, so nothing
drains events; autosave is off until the world is presented. The main thread
reads exactly one `volatile int` from the worker — the tick number. Verified,
not assumed: 150 ticks from one seed stepped on the main thread and on a
worker encode to a byte-identical `WorldSnapshotCodec` blob.

Measured tick cost, same code, same seed: **0.84 ms headless (.NET 9 Release)
vs 6.51 ms in Unity Mono**, and 12.07 ms with the §30.14 flight recorder on —
which every development build enables. The wind therefore switches the recorder
and `SimTrace` off for its duration and restores them in a `finally`; no
simulation system branches on the event ring (only the snapshot exporter reads
it), so the outcome is unchanged. The Player's scripting backend moved to
IL2CPP for the same reason.

The load log states both numbers separately — ticks/s on the worker and the
share of the load window the wind occupied — because dividing ticks by the
whole window would report a slow wind whenever content was the thing that took
long.

The wind starts from the
RESTORED state (v2: load first, then simulate the absence) and finishes
BEFORE any view spawns — the player returns to "time really passed":
resources regrown, needs drifted, maybe someone got bitten.

"Before any view spawns" is enforced by `LoadingScreen.IsReplaying`, and
that curtain goes up **before `Configure()`**, not when the wind loop
starts: the runner reports `IsReady` the instant `Configure` returns, so a
curtain raised any later leaks one or two frames in which the renderer
builds the ENTIRE scene (terrain, actresses, props) on the pre-wind state —
which the wind then invalidates. Order is: curtain → create world → restore
blob → wind → curtain down → views build once (phase 3).

**Content is warmed TWICE, around the wind, and the curtain waits for both.**
`ScenePrewarm.ForWorld` is the single place that answers "what does THIS world
need to show", and the single place a new content family is added; a family
forgotten there does not break, it silently returns to the lazy path, i.e. a
blocking disk read in the first frame of play. It covers what depends on world
state — worn and dropped garments, hairstyles, prostheses — and runs once in
`Bootstrap` (requests do not block, so the wardrobe downloads alongside the
wind) and once after the wind, for the difference: over a game day of offline
time a colonist changes clothes, dies in something else, loses a limb and gains
a prosthesis (§50), and a new woman arrives with her own hair (§46). Every door
is idempotent, so the second pass only files what is missing.

Content that does NOT depend on the world is warmed unconditionally and stays
out of that walk: icons — all of them, since they live in ONE 0.73 MB bundle,
against 712 bundles and 1.99 GB for wear — and item/weapon models, which
`Resources.LoadAll("HexLive/Objects")` takes as a whole folder (64 assets,
8.3 MB), so a new axe warms itself with no list to maintain.

While winding, the screen shows a big **«День N · ЧЧ:ММ»** readout using the
sim's own clock formatter. The displayed day is the **calendar day**
(`EnvironmentSystem.CalendarDay`): the tick-day starts at 06:00 (tick 0 =
Day 1, 06:00), but the day NUMBER rolls over at **midnight** — 23:59 of
day N is followed by 00:00 of day N+1, not by six more hours of day N.
Every player-facing day readout (loading wind, weather widget, game
history, end summary) uses this helper; sim logic (raids, storms,
spoilage) stays on raw tick-days.

### 41.4 Main menu (iteration 38, restyled iteration 43)
The loading screen opens with a MENU over the island art, before any world
exists — a dark rounded card docked bottom-left, icon rows painted with
Painter2D (no texture assets): **«Продолжить»** (gold primary; dimmed and
unclickable without a save), **«Перезапустить остров»** (keeps the selected
save and creates a NEW slot with the same seed/mode from day 1; dimmed without
a save), **«Миры»** (always opens the local save catalog, even when Continue
points to the last server), **«Новая игра»** (creates a new slot and rolls a
fresh seed), **«Настройки»** and **«Персонажи»** (visible placeholders,
disabled for now), **«Выйти из игры»** (`Application.Quit`, stops play mode
in-editor), then a divider and the tagline («Исследуй. Строй. Выживай.»).
The world is bootstrapped only after the choice — the runner sits
unconfigured (renderer/panels all guard on `IsReady`), so the menu costs
nothing. After the click the flow is §41.1 unchanged: restore → offline
wind → spawn → warm-up → fade → Jana.

### 41.5 Wake-up grace (iteration 38)
Waking from any Sleep (bed / leaf mat / ground) sets
`Mind.WakeGraceUntilTick = tick + AiBalance.WakeGraceTicks`. While in grace the
DecisionSystem does not score goals — the NPC simply STANDS where she slept,
coming to her senses; no instant errands off the pillow, and the presentation
GetUp clip has room to play without foot-sliding (exported as
`NpcSnapshot.IsWaking`).

**r2 (bug #1): the grace is sized by the actual get-up clip, 18 ticks.** The
old 12 (~3 s) was shorter than the GetUp clip («Situp To Idle», 132 frames @
30 fps = 4.4 s = 17.6 ticks), so the sim started walking her ~1.4 s before the
clip finished and her feet slid along the ground. The fallen chain's StandUp
(«X Bot@Standing Up», 1.67 s) is covered by the same number. The end of a §110
crying breakdown gets the SAME grace (it stands up with the same GetUp clip);
being ripped out of lying by a wound / coma / raid deliberately does not.

**r3 (bug #95): interrupting Sleep is also waking up.** A replacement plan —
including a manual Kenshi-style order — may be accepted and retained, but
the manual-order boundary arms the same 18-tick grace before clearing Sleep,
and both pathfinding and execution wait for it. Thus an order given from bed is
queued through GetUp instead of translating or interacting in the lying pose.


### 41.6 Занавес на ЖИВОМ мире (сервер) — ждать по-другому
Подключение к серверу (§83) идёт по своей ветке загрузчика: ни сида, ни
восстановления, ни намотки офлайна — мир уже стоит на своём тике и **не
останавливается ради загрузчика**. Отсюда два правила, которых нет у
локального пути (там мир на паузе и потому неподвижен):

- **Список тел, чьей готовности ждёт занавес, пересобирается каждый кадр.**
  Ростер снимается один раз, до прогрева панелей, а колонистка за это время
  может умереть: её вид уезжает из живого реестра в трупный (§28.15F), и
  «готова ли она» после этого не станет правдой НИКОГДА. Пропавшая из снимка
  снимается с ожидания записью в лог.
- **Ожидание ограничено (30 с), и это не отмена правила «каждая начатая
  задача обязана завершиться».** То правило — про Addressables, которые
  завершают операцию всегда; здесь же ждут ещё и колонистку, которую мир
  меняет прямо во время ожидания. Занавес, переживший загрузку, — игра, в
  которую нельзя играть; недошитая причёска — кадр, который догонит через
  секунду. По истечении срока занавес поднимается силой, а в лог уходит
  ошибка.

**Ждать молча запрещено.** Раз в 5 секунд ожидание печатает, КОГО именно оно
ждёт: остаток очереди контента и по каждой неготовой колонистке — причину
поимённо («вида нет», «умерла и уехала в трупы», «причёска едет», «протез
LegL едет», «вещь 'wear.top' не надета»). Снаружи все пять фаз удалённой
загрузки выглядят одинаково («экран не пропал»), и без имени виноватого
следующий диагноз — ставка, а не работа (§109.16). Вехи фаз (подключился,
столько-то колонисток, занавес ушёл) тоже идут в лог.

### 41.7 Погашенная актриса дошиться не может (баг #182)
Занавес висел вечно при подключении к серверу, и причина оказалась не в связи.
Замер назвал виноватых поимённо: двое из шести — `причёска едет (1)`, очередь
контента стоит на двух задачах вида `HairColour`. Живой редактор досказал
остальное: у обеих `activeInHierarchy = False`.

**Unity убивает корутины ВЫКЛЮЧЕННОГО объекта — молча, без исключения.**
Причёска ехала корутиной на самой актрисе, и смерть между
`ContentQueue.Begin` и `End` оставляла очередь навсегда непустой, а
`_pendingHairLoads` — навсегда единичным. Гасил их культинг восприятия: девушки
соседних лагерей (§146 Feud) не видны, пока их не увидит кто-то из наших, а на
удалённом мире глаз у вида нет вовсе (`RebuildFogState` читает `Engine`, которого
в удалённом режиме не существует), — так что ривалки гасли ВСЕГДА. Гейт
`_cullInitialBuildDone` был поставлен ровно против этого класса зависания
(#146), но покрывал только первую сборку кадра, а причёска приезжает много
кадров спустя.

Два правила, каждое из которых закрывает беду само по себе:

- **Учёт загрузки не живёт на объекте, который кто-то вправе выключить.**
  Корутины контента крутит постоянный хозяин (`ContentCoroutines`), а не
  актриса: материал и префаб одинаково нужны и погасшей. Одежда, протезы и
  иконки этим не болели — они считаются по `Completed` у Addressables, а не
  корутиной, и потому невыключаемы; болела только причёска, обе её очереди.
- **Пока занавес поднят, актёров не гасят.** Гейт культинга расширен с «первая
  сборка позади» на «загрузка закончилась» (`LoadingScreen.IsActive`). Под
  занавесом ривалок всё равно никто не видит, а дошиться они обязаны — их ждёт
  ростер §41.6.

### 41.8 Каталог локальных миров: сервер и новая игра ничего не затирают

Одиночный `hexlive_save.dat` был скрытым глобальным слотом: новая игра
удаляла прежнюю колонию, а после посещения сервера «Продолжить» вело обратно
на сервер и не давало выбрать оставшийся локальный мир. Локальная игра теперь
имеет каталог без фиксированного числа слотов:

```text
Application.persistentDataPath/saves/<world-id>/
├── world.dat       HXLV header + WorldSaveSerializer blob
├── world.json      id, created/lastSaved UTC, seed, mode
└── preview.jpg     640×360, последний кадр игровой камеры
```

- `world-id` генерируется игрой (`UTC timestamp + seed token`), не вводится
  игроком и проходит строгую проверку перед сборкой пути. Коллизия добавляет
  числовой суффикс; каталог не имеет лимита слотов.
- Выбранный id хранится в `HexLive.LocalWorldId`. `TryReadHeader`, restore и
  каждый autosave работают только с ним. Подключение к серверу не меняет этот
  id и ничего не пишет: удалённый backend по-прежнему не поддерживает client
  save.
- «Новая игра» всегда выделяет новую директорию. «Перезапустить остров» тоже
  выделяет новую директорию с прежними seed/mode; старый прогресс остаётся
  отдельной карточкой. Удаление возможно только явно из карточки локального
  мира и требует отдельного подтверждения «Удалить навсегда»; серверные миры
  этим локальным API не затрагиваются. После удаления выбранного мира его
  `PlayerPrefs`-id очищается, а каталог выбирает следующий доступный мир.
- Отдельная UI Toolkit-панель «Миры» доступна независимо от того, куда ведёт
  «Продолжить». Карточка показывает превью, локализованное название режима,
  календарный день, seed и локальное время последней игры; кнопка загружает
  именно этот id. При выборе любого локального пути `SessionConfig` явно
  возвращается из Remote в Local ДО создания backend.
- `preview.jpg` снимается при успешном сохранении отдельным рендером главной
  камеры, поэтому UI/HUD не попадают в обложку. Если кадра ещё нет или файл
  повреждён, карточка использует штатный island art; само сохранение от
  отсутствия превью не зависит.
- Старый одиночный `hexlive_save.dat` мигрирует только после чтения валидного
  HXLV-заголовка. Нечитаемый legacy-файл и нечитаемые каталожные директории не
  удаляются автоматически: они остаются на диске для ручного восстановления,
  но не предлагаются как загрузимые миры.
