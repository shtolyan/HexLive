# Подпись приложений HexLive на macOS

Обязательное правило для всех агентов и билдеров (§160): готовые клиент и
Agent Studio публикуются только с постоянной сертификатной подписью и после
`codesign --verify --deep --strict`. Сбой проверки останавливает публикацию.
Не обходить его через `--sign -`, смену сертификата или ручное переключение latest.

## Штатные команды

Из корня любого checkout:

```bash
python3 Tools/macos_signing.py --check-identity
python3 Tools/build_release.py --release
python3 Tools/package_agent_studio.py --binary-dir Build/dotnet/bin/HexLive.AgentStudio/Debug/net9.0
```

Первая команда проверяет настройку и пробную подпись временной копии системного
исполняемого файла тем же сертификатом (ожидание Keychain не более 30 секунд).
Наличие сертификата в списке identity само по себе не доказывает доступ к ключу.
Пробный файл удаляется; приложение и опубликованные версии не меняются.
Клиент без `--release` тоже обязательно
подписывается. Studio упаковывает уже скомпилированную программу; для Release
сборки укажите соответствующий каталог или используйте значение по умолчанию.
Проверка сертификата встроена в оба сборщика, вручную запускать её необязательно.
Правило о закрытом Unity Editor перед компиляцией из `CLAUDE.md` сохраняется.

Оба сборщика вызывают `Tools/macos_signing.py` после всех изменений внутри `.app`
и до публикации. Helper подписывает вложенный код, закрепляет внешний identifier
и строго проверяет результат. Больше ничего внутри подписанного `.app` менять
нельзя. Проверенный выпуск публикуется новой версией с атомарным latest-ярлыком;
старые версии сохраняются. Любой новый macOS-упаковщик должен повторять этот путь.
Отдельный тестовый клиент `Tools/build_hut_test.py` также проходит preflight и
общую сертификатную подпись; исключения для ad-hoc у тестовых `.app` нет.
Промежуточный native bundle `Tools/build_macos_permissions.py` может иметь ad-hoc
подпись в исходниках: при упаковке приложения он переподписывается сертификатом
вместе со всем вложенным кодом. Это не самостоятельное приложение.

Постоянные bundle ID:

| Приложение | CFBundleIdentifier и identifier подписи |
| --- | --- |
| HexLive | `com.juilcylove.hexgirls` |
| Agent Studio | `com.hexlive.agentstudio` |

Не использовать у Studio унаследованный случайный identifier .NET apphost.
Сборщики передают helper ожидаемый bundle ID; несовпадение — ошибка.

## Общая настройка, независимая от вкладки

Выбранный публичный SHA-1 отпечаток сертификата хранится в
`~/.config/hexlive/macos-signing-identity`. Его читают все задачи и checkout,
запущенные от того же macOS-пользователя. Закрытый ключ остаётся в Keychain.
Переменная `HEXLIVE_MACOS_SIGN_IDENTITY` имеет приоритет; использовать её только
для явно согласованной настройки билдера, не для обхода ошибки сертификата.

На Mac игрока выбран `Apple Development: Anatolii Sheshenin (687ZHTKUL3)`,
отпечаток `D50F94D376CCA3B2727703A6A28D971D83F23905`, Team ID `89R3XSKFQJ`.
Не выбирать автоматически другой из нескольких доступных сертификатов.
Preflight проверяет выбранный отпечаток через `security find-identity -v -p codesigning`.
Отсутствие настройки, сертификата/закрытого ключа или валидной identity — ошибка.
Недоступный Keychain при фактической подписи также останавливает публикацию.

На другом Mac/CI владелец должен установить тот же сертификат с закрытым ключом
в Keychain билдера и настроить его публичный отпечаток. Одного файла `.cer`
без закрытого ключа недостаточно. Не хранить закрытый ключ, пароль или `.p12`
в репозитории. Продление/смена сертификата — явная настройка владельца; проверить
сохранение identity и системных разрешений перед публикацией обновления.

Если ограниченная среда агента не видит Keychain, проверить теми же инструментами
в разрешённой нативной среде. Это не повод менять identity или отключать проверку.

## Что подпись обеспечивает

Постоянные сертификат и bundle ID позволяют macOS узнавать обновления приложения.
Запросы доступа к сохранённым ключам выполняются на старте, результаты кэшируются
на сеанс; диалог не переносится на первую реплику. Пользователь выбирает
«Разрешать всегда» для нужного ключа и разрешает микрофон. Первое подтверждение,
отзыв разрешения, смена identity или блокировка Keychain могут вызвать новый запрос.
Подпись не выдаёт доступ ко всем ключам и не заменяет согласие пользователя.

Текущий путь — локальная Apple Development подпись. `--release` означает
оптимизированную сборку, а не публичную нотарификацию. Для скачивания на чужие Mac
нужны Developer ID Application, корректные Hardened Runtime entitlements,
secure timestamp, нотарификация и прикреплённый ticket. Apple Distribution
относится к другому каналу распространения и не заменяет Developer ID Application.
Существующая Developer ID/Distribution подпись в release сохраняется только после
проверки; это само по себе не проверка нотарификации. Публичный канал следует
настраивать отдельно для обоих приложений, включая .NET и аудиобиблиотеки.

Источники Apple: [identity и разрешения](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements),
[Developer ID](https://developer.apple.com/developer-id/),
[нотарификация](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution).
